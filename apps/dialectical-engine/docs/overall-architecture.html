Dialectical Engine Overall Architecture

Local-first debate-generation platform: browser + Next.js UI, same-origin proxy, FastAPI coordinator, SQLite persistence, pull-based workers, model adapters, SSE streaming, and optional Cloudflare Tunnel ingress.

Timeline: who talks to whom, and when

T0
Runtime starts
make dev starts FastAPI on :8000, Worker A, and the source-controlled web proxy on :3000. The proxy starts Next.js internally on :3001. In installed mode, launchd services can replace the dev launcher.
T1
Worker → models
The worker loads ~/.dialectical-worker/config.toml, probes enabled adapters, and only advertises capabilities whose health checks pass. This keeps routing honest: the coordinator schedules only models the worker says it can actually run.
T2
Worker → Coordinator
The worker registers with the user token, receives a per-worker token, saves it, then sends heartbeats. After that, job calls authenticate with Authorization: Bearer <worker_token> plus X-Worker-ID.
T3
User → Web
A browser reaches the same origin locally or through Cloudflare. Public read pages need no token; new debates, settings, admin, feedback, and regeneration use the user bearer token stored in browser localStorage.
T4
Web Proxy → Next / FastAPI
The proxy sends UI routes to Next.js and API/SSE routes to FastAPI. This gives local and tunneled users one origin while keeping the backend and frontend as separate processes.
T5
Browser → Coordinator
POST /api/debates creates a debate. The default V2 path requires a real codex-gpt-5.5 worker online, creates the root claim, branch, four POV nodes, and queued v2_pov jobs in SQLite.
T6
Browser → EventBus
The browser subscribes to GET /api/debates/{id}/events. The coordinator's in-process EventBus replays recent events, then streams live tokens and lifecycle events as Server-Sent Events.
T7
Worker ↔ Coordinator
Workers long-poll /api/workers/{id}/poll. The coordinator claims an oldest compatible pending job, returns the rendered prompt, and updates worker/job state so no inbound worker port is required.
T8
Worker → Model adapter
The worker invokes the selected adapter: Codex CLI, LM Studio's OpenAI-compatible local API, Gemini, xAI, Claude, Ollama, or mock. The coordinator never shells out to these adapters for normal generation.
T9
Worker → Coordinator → Browser
As the model emits text, the worker posts chunks to /api/jobs/{job_id}/stream. The coordinator appends the buffer, renews the job deadline, and publishes SSE token events to connected browsers.
T10
Worker complete
The worker posts /api/jobs/{job_id}/complete. The coordinator validates the strict JSON contract, materializes nodes/generations/provenance, may enqueue follow-up jobs, persists everything, and emits completion events.
T11
Coordinator synthesis/scoring
After all POV work is complete, the coordinator queues v2_synthesize. Scoring can run through an internal background job/provider registry and stores AnalyzerRun/NodeScoringResult/cache data instead of pretending unavailable scores exist.
T12
User reads result
Public readers call GET /api/debates, GET /api/debates/{id}, scoring reads, SSE, or markdown export. Admin-only mutations remain token-gated.

Why there is a web proxy

  • • It keeps the browser on one origin: local :3000 or the Cloudflare host.
  • • It routes API, docs, health, and SSE traffic to FastAPI.
  • • It routes all UI assets/pages to Next.js on the internal port.
  • • This avoids baking a public API domain into the Next bundle.

Why workers pull jobs

  • • Workers can run on the Mac mini, another laptop, or behind NAT.
  • • The coordinator never needs to open a connection into a worker.
  • • Worker capabilities are discovered from real adapter health checks.
  • • Failover is simple: stale/deadline-expired jobs are requeued.

Why SQLite is central

  • • It is the durable source for debates, nodes, jobs, workers, generations, scoring, and provenance.
  • • FastAPI owns writes through SQLAlchemy plus explicit write-lock helpers.
  • • SSE is live/in-memory, but durable state is read back from SQLite.
  • • Local-first deployment stays simple: no external database is required.

Why Cloudflare is optional ingress

  • • The app already works on localhost.
  • • Cloudflare Tunnel exposes the same web proxy publicly without traditional hosting.
  • • The tunnel targets http://127.0.0.1:3000, not each internal service separately.
  • • DNS/Romarg setup only changes public reachability, not app internals.

Auth boundaries

  • • Public reads: debates list/detail, SSE, export, backend status, scoring reads.
  • • User bearer token: create debate, settings, admin, feedback, regeneration, worker registration.
  • • Worker bearer token: heartbeat, poll, stream, complete, fail.
  • • Tokens are hashed in coordinator storage; worker token is saved in the worker config.

What is live vs durable

  • • Live: SSE token stream and bounded event history in the EventBus.
  • • Durable: jobs, stream buffers, nodes, generations, synthesis, scoring, provenance in SQLite.
  • • If a browser reconnects, it gets recent events and can re-fetch durable debate state.
  • • If a worker dies, the coordinator requeues active/stale jobs instead of losing the debate.
