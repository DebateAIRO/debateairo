# Register 12 on the v3 preview: the answer writer v3 and answer checker v2 (runbook delta)

Status: DRAFT, written 2026-10-12 from branch `fix/2026-10-12-answer-writer-v3`. **Nothing in it has been
run.** It is a delta to the code-only release runbook the R12, R13 and R14 releases used
(`RUNBOOK-R12-CODE-RELEASE.md` in the owner's handover folder `2026-10-10-part-i`, phases F, P, W, C, X and
the RB blocks) and borrows the publish steps of `RUNBOOK-FIVE-AI.md` (R11-01 to R11-03, W2-04 to W2-07),
which made version 11. Every server step still needs the owner's yes in chat; the runner start is its own yes.
No agent reads, prints or copies a key, a password, an email address or an `.env` value.

## 0. For the owner, in plain words

**What changes.** Two of the instructions the AIs are sent, with the wording you approved on 2026-10-12:

- the **answer writer** is told to write the answer for the person who asked, never printing a score, a
  number taken from the debate's material, a field name, a point id, or how the debate was run;
- the **answer checker** is told to check exactly that, besides fairness, agreement with the label and no
  overstatement.

Each instruction is sealed by a fingerprint, and the settings (the register) carry the fingerprints. A changed
instruction is a new sealed version, never an edit, so the settings need a new version too: **version 12**.
It differs from version 11 in exactly two rows, the two fingerprints (measured on the Mac against the export
of version 11 taken for the practice debates of 2026-10-12), plus the usual source reference of
`nodeRuntimeVersion`, which every publication re-measures.

**New safety check.** The debate worker (runner) now refuses to start when the settings version it is
pinned to does not carry the fingerprints of the instructions its code sends (`REGISTER_PROMPT_CONTRACT_HASH_MISMATCH`,
with the row and both values). Before this, the new instructions would have been recorded under the old
fingerprints with nothing red anywhere. So version 12 must be published and pinned before the new runner
starts; with version 11 still pinned, it will not start (by design).

**Before the upload: a practice debate on version 12.** Your rule is that a practice debate with all real AIs
passes before any upload. The practice tool now has `--register-next`: it copies version 11 as always, then
builds version 12 from the new code exactly as the server's publish step will (same tool, same inputs: the
DeepSeek checker, rotation on, the measured runtime of version 11), and runs the debate on it. Its progress
line and report name the rows that changed; they must be exactly the two fingerprints.

**Downtime.** The same short block as R12 to R14, about 5 minutes longer (publish and a second proof).

**Rollback.** Version 12 stays sealed and unused; the old release goes back on version 11 (section 4).

## 4. Rollback

- **During the window, before the publish:** RB-1 unchanged (nothing written).
- **After the publish (version 12 exists):** version 12 stays sealed and unused; it is never deleted or edited.
  Back to the old release = RB-2 with three differences: put back `$S/native-plan.before.json` (the verify plan
  of version 11), set `REGISTER_VERSION=11` in `api.env` and `runner.env` (the copies in `$S`), and re-pin the
  old launch plans (they carry publication 11). The old code has no fingerprint check; on version 12 it would
  record its v2 instructions under the v3 fingerprints, so it must go back to 11 with it.
- **The next publication after a rollback** must be planned from version 12 (`plan` refuses a base with a newer
  version above it): run it with `--from` the kept `$ART/native-plan-verify.json` of W-02, which names 12. The
  owner then reviews a delta measured against 12, not against the running 11.
- Do not delete the old release folders or plans until the new release has run at least a day.
