**BLOCKING**

1. **Registration is now fire-and-forget and non-durable (regression from B2's fix).** `POST /v1/auth/register` returns 202 "verification instructions will arrive" with *nothing* persisted; the registration exists only as a `PendingRegistration` in the unbounded in-process `Set` at `apps/api/src/registration.ts:231`, holding plaintext email, plaintext recovery email, password hash, raw IP and raw UA. Failures are swallowed by `console.error("[AUTH_REGISTRATION_PROVISION_FAILED] code=PROVISION_FAILED")` at `:356-358` â no identifier, so the loss is untraceable. Three parties reproduced independently: at 100 concurrent registrations, ~10.5 s window with 12-13 accepted-but-unwritten accounts; no shutdown hook in `main.ts`. A DB blip, disk-full or KEK error converts a 5xx into a lie to the user. This is a durability change to a ratified endpoint and is the single clearest answer to "did the fixes break anything".

2. **A blank or whitespace-only `User-Agent` erases the audit trail and breaks all three auth routes.** Verified at source: `hashAuditContextValue` throws on `value.length === 0` (`packages/crypto/src/index.ts:365`); `sourceContext` (`apps/api/src/registration.ts:216-225`) validates `ip` and `requestId` for emptiness but **not** `userAgent`; `sourceFor` (`apps/api/src/index.ts:194-203`) substitutes `"unknown"` only when the header is *absent*, not when it is present-and-blank. Reproduced over real sockets by three parties: verify â 500 `CRYPTO_KEY_INVALID`, resend â 500, register â 202 with zero accounts and zero mail. The escalation is the finding: `appendAudit` hashes the UA *inside* the transaction, so the throw rolls back the audit row â six unauthenticated verify attempts produced **zero** audit rows, and the `rate_limit_refused` aggregate vanished *silently* precisely because B5's new `.catch()` (`:322-327`) now swallows it. B4 and B5 compose into audit evasion by one header. Bounded at 30 unaudited attempts per IP per window by the limiter, not unlimited. Fix is two lines: clamp empty UA to `"unknown"` in `sourceContext`. (Attribution to B4 is sound inference, not git-provable â the tree is one squashed commit and `registration.ts` is untracked.)

3. **The limiter fix denies new keys while below-limit buckets exist (regression from B1's fix).** B1 itself is genuinely closed â `retain` (`:97-114`) evicts nothing, and fresh-limiter probes give exactly the ruled 20/30/15. But the refuter's correction stands and sharpens the charge: the packet *did* order "a saturated map fails closed on new keys", so refusing on a fully-at-limit map is ruled behaviour and the lane's "traded security for availability" headline is rebuttable. The unruled part is that round 4 also refuses when **below-limit, non-served buckets exist** â round 3 served 100/100 brand-new visitors there, round 4 serves 0/100. Saturating the single global 4096-bucket map costs 3,840 requests (resend, sustainable at 1.07 req/s, 60-min buckets â the cheapest vector) or 3,901 (register), from one `/64`, and takes all three routes offline for everyone not already in the map. **No attacker is required:** the organic ceiling refuses the first legitimate user at signup #683 for a full register+verify+resend journey. Plus, unreported by the lane and measured by the refuter: capacity refusals charge `take(ip)` before the address take fails, so a victim retrying through a 60-second outage ends at 20/20 on its own bucket and is locked out for the remaining 14 minutes *after* capacity frees. Refuter verified the fix is ~4 lines on top of round 3 (restore eviction; never evict a bucket at/over limit, never evict either key of the request being served) and that it passes the shipped test unchanged while serving 100/100 at capacity.

4. **Request timestamps are now stamped at provisioning time, not request time (regression from B2's fix).** Confirmed at source: `provisionPendingAccount` (`:369-417`) takes `const now = this.clock()` fresh, and `PendingRegistration` (`:208-214`) carries no timestamp â so `adultAffirmedAt`, the audit `occurredAt`, and `verificationExpiresAt` all record when the queue drained, not when the user acted. **RESIDUALS to record**

1. **Two-phase cross-request timing oracle.** Fire k register requests at candidate addresses, wait ~120 ms, time one request of your own; a ~500 ms answer identifies the probed set as already-registered. **NEW TICKETS**

1. **Audit chain-head lookup is a double sequential scan inside a global advisory lock, on an unprunable table that unauthenticated traffic can grow forever.** `identity.ts:93-101`: lock, then an anti-join over the whole `audit_event` table. Measured 0.37 ms @ 1k rows â 163 ms @ 500k; end-to-end verify latency 57.8 â 117.7 ms; 8.7k temp buffers spilled. Every well-formed-but-wrong verification token writes one permanent row (~2,880/IP/day), 0030 grants only SELECT/INSERT with a reject_mutation trigger, so it is monotonic and self-accelerating â a different class from a transient stall. **T1 does not touch it** (argon2id runs *before* the lock), so the "already ticketed, do not re-block" disposition rests on a mis-attribution. Fix: one-row chain-head pointer or monotonic sequence.
2. **Register's existing-address branch writes no audit event, while resend's does** â an enumeration sweep against known accounts is invisible. This also points at a cheaper B2 fix than a worker thread: append a DENY registration-attempt event on the existing branch, on-path, mirroring `prepareVerificationResend` (`identity.ts:329-366`) which already audits both branches symmetrically. No queue, no drain, no shutdown hook, truthful `occurred_at`, no cross-request contamination â and it closes the audit blind spot. The correct pattern already exists one file over.
3. **The limiter has no capacity, size or metric accessor.** A policy refusal and a capacity refusal of a first-time visitor return byte-identical `{allowed:false, scope:"ip"}`. A total registration outage presents to operators as ordinary 429s and to the audit table as client-side rate limiting.
4. **`bucket_capacity` accepts values that brick the service.** Schema is `z.number().int().positive()` (`auth-policy.ts:47`); at capacity 1 the limiter refuses 100 % of traffic. Every consume needs two buckets, so the floor must be â¥ 2Ã expected concurrency, and 4096 should be derived from expected concurrency rather than flat.
5. **`trustProxy` is not set** (`Fastify({logger:false})`, `ip: request.ip`, no reverse proxy in `deploy/`). Behind any proxy the entire user base collapses into one 20/15-min bucket. Ticketed separately already, but **every severity number in the B1 analysis is conditional on an unpinned deployment topology** and that condition must be stated.
6. **Decide the disposition of pre-0031 audit rows.** They carry non-NULL `actor_ciphertext` (encrypted actor material) and cannot be updated or deleted through any supported path. This interacts with VR-3 for any account deleted after those rows were written, and it determines whether 0032 lands as `NOT VALID` plus a backfill or as an explicit S2 amendment.
7. **0032 narrows a ratified S2 contract** â needs an amendment on the record, not a quiet acceptance-test edit.
8. **Refusals shed no load.** All three routes await a repository lookup *before* `limiter.consume` (the refusal audit needs the actor token), and refused register/resend requests still hold the full 500 ms floor. The limiter protects neither the DB nor the connection pool. Also: `requestId` is validated strictly enough to 400 a request but, since B4 removed `requestIdSha256`, is never persisted anywhere â dead weight that can still reject traffic.
