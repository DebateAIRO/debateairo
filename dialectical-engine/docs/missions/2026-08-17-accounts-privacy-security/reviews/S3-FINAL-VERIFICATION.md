## 1. VERDICT

**DO-NOT-CLOSE.**

Two of the ticket's own contract items are demonstrably not met â the rate limiter it was built to own fails *open* and stays open, and the account-existence oracle R1 was reworked to close is back through a different branch â and one permanent, unrepairable privacy defect (an unsalted user-agent hash) is being written into an append-only table that is still empty today. Every blocking item below is a contained fix, not a redesign; VR-3 itself holds, so this is a "fix seven things and re-verify," not a rewrite.

## 2. BLOCKING

**B1. The rate limiter fails OPEN, and that is where a flood lands.** `apps/api/src/registration.ts:96-123` (`retain`) is called twice per `consume` (IP then address). At bucket capacity the second call finds the IP bucket the first call just created as the only below-limit candidate (eviction scan `:110`, insertion-order iteration) and evicts it. The key's counters can therefore never accumulate. Two independent probes against the real exported class measured one source IP getting **200/200 register (policy 20), 500/500 verify (policy 10), 500/500 resend (policy 3)**. Cost to reach: ~820 IPs / 16.4k requests, or simply overshooting a saturating flood. Lane and refuter disagreed on characterization â lane called it "a cliff exactly at belowLimit == 1," refuter proved the general rule is that only `floor(belowLimit/2)` distinct keys can retain state, and that the fail-*closed* state everyone credited as "packet-prescribed" is metastable: `sweepExpired` (`:85-94`) drops one bucket below limit on the first expiring timestamp and the map slides into the open state. **The refuter is right, and the fix must follow the general rule** â "evict at most once per consume" alone does not repair the two-rotating-keys case.

**B2. The account-existence oracle is reopened, wider than the bug it replaced.** `registration.ts:255-259` pads and never clamps. The new-address branch does strictly more *blocking* work than the duplicate branch: a second argon2id (`packages/db/src/identity.ts:88`, ~25-28 ms measured), the global `pg_advisory_xact_lock('identity:audit-chain')` (`:89`), the DEK file write inside that lock, and five extra round trips â while the duplicate branch returns at `registration.ts:407`. Two harnesses written independently agree within 5%: at **4 concurrent registrations the distributions are disjoint** (existing 513-615 ms, non-existent 904-971 ms), so one request classifies an address with zero error, and 4 in-flight registrations fit inside one IP's own ruled budget of 20/15 min. The ruled `enumeration_tolerance_ms: 100` is read by no product code â only by tests. Caveat: **both harnesses were in-memory, not Postgres**, so require a real-stack repro as the fix's acceptance evidence. The asymmetry itself is unarguable from source. Contract item 4 fails.

**B3. The ruled 60 s resend cooldown does not function, and the first email ships a dead link.** `prepareVerificationResend` reads `verification_last_sent_at` (`identity.ts:341`), but the only writer is `recordVerificationDelivery` (`identity.ts:252`), which runs post-floor, post-response, off `setImmediate`. Register â resend 200 ms later delivers 2 mails where the cooldown intends 1, and the resend's UPDATE (`identity.ts:346-351`) rotates the token hash *before* the registration mail is dispatched â so the user's first email arrives already invalid. Worse than the lane stated: `dispatchVerification` swallows record failures (`registration.ts:333-335`), so one failure leaves the column NULL **permanently** and the cooldown inert for that account forever. Fix: set `verification_last_sent_at` in the same transaction that mints the token hash.

**B4. Unsalted SHA-256 of the user agent, written into the immutable audit table.** `packages/db/src/identity.ts:107-111` stores `userAgentSha256` and `requestIdSha256` as bare SHA-256. Recovering a deleted person's exact browser/OS string from a public UA corpus is free and permanent; the table can never be repaired. Lane and refuter agree; nobody defended it. This is exactly the argument V accepted for VR-7 (append-only â salt unrotatable â a fast hash over a small domain is fatal) applied to the one field VR-7 did not name â and the production table is still empty, so this is the only moment the fix costs nothing. Fold `requestIdSha256` into the same change by **deleting** it: the refuter is right that it is redundant with the plaintext `occurred_at` in the same row (it hashes fastify's `req-<n>` counter, default because `apps/api/src/index.ts:143` sets neither `genReqId` nor `requestIdHeader`), so it is the *least* consequential item on the erasure lane's list, not the sharpest.

**B5. A rate-limit refusal can become HTTP 500 carrying the raw Postgres error text to an unauthenticated caller.** `registration.ts:322` awaits `recordRefusalAggregate` with no guard, while the timer path at `:293-296` has `.catch()` + operator log. `index.ts:185-190` returns `message: knownError.message` for anything that is not an `AuthFlowError`. A DB fault on window rollover converts a 429 into a 500, leaks driver text, and loses the audit silently. Found independently by two refuters. One-line fix.

**B6. Drizzle model/migration drift â six columns modelled on the wrong table.** `migrations/0031_registration_verification.sql:21-27` adds `verification_token_hash`, `verification_expires_at`, `verification_consumed_at`, `verification_last_sent_at`, `delivery_status`, `delivery_error` to `identity.channel_binding`; `packages/db/src/schema.ts:42-47` puts all six on `mfaFactor`, and `channelBinding` (`:59-68`) has none. I verified both ends directly. Green only because `identity.ts` uses raw SQL and the architecture contract test pins migration 0030 only. S4 (MFA) hits it first. Six-line move.

**B7. `pnpm-workspace.yaml:11` contains a non-boolean placeholder:** `argon2: set this to true or false`, left by an abandoned `pnpm add argon2` (`node_modules/.pnpm/argon2@0.45.1` mtime 15:14:49, one second before the file was rewritten; `argon2` appears 0 times in `pnpm-lock.yaml`). Out of the packet's file contract, and it falsifies the progress log's "scope audit found only packet-authorized paths." Delete the line.

**Fold into the same commit (one-liners, no separate review):** `"--"` before the recipient at `apps/api/src/mail-channel.ts:71` plus rejecting a leading `-` in `validEmail` (`registration.ts:214`); a `.max()` on `memory_cost_kib`/`iterations` in `packages/register/src/auth-policy.ts:22-29`; re-read the clock after the repository await in `verifyEmail` (`:473`) and `resendVerification` (`:506`); correct the false claim in `migrations/0031` line 4-5 and the stale "HMAC key" wording in `packages/crypto/SECRET_STORE_LAYOUT.md:14`; seed the five auth-policy rows in `persistBootstrapRegister` (`packages/register/src/index.ts:462-487`).

The missing `--` is a genuine CWE-88 hardening defect worth the one-token fix; **it is not CVE-2016-10033-class and should not be reported to V as a remote file-write.**

## 3. RESIDUALS worth recording

1. **The auth-policy register rows are defined but never seeded, so the API cannot boot.** `main.ts:35` calls `readAuthPolicy`, which throws `AUTH_POLICY_UNRESOLVED` (`auth-policy.ts:182`) when any of the five rows is missing. I verified nothing in `migrations/`, `acceptance/`, or `persistBootstrapRegister` writes them; the only references are the definition, a re-export, and two test files that bypass the DB path entirely â so `readAuthPolicy` has zero coverage. *Acceptable now* because it fails closed, never open, and an S3 account is unusable until S4/S5 anyway. *Changes* the moment anything must start the API. Cheap enough that I put it in the fold-in list.
2. **`ipArgon2id` permanently links a deleted account to surviving named accounts on the same household/NAT IP, within a salt epoch.** This is VR-7 working as ruled, not a defect â and the refuter is right that "unrotatable" is wrong: rotation is shipped and tested (`tests/integration/registration-database.test.ts:349`). But V should see the numbers before more rows accrue: the ruled parameters are exactly the schema floor (19456 KiB / t=2 / p=1 â the OWASP *password* minimum, ~26 ms/call measured), a full IPv4 sweep costs roughly $60-300 of rented GPU, and the realistic attack ("was this IP ever here?") costs **one hash at any parameter**. The password row in the same file uses 65536/3. *Changes* if V decides the intent was inversion resistance rather than sweep cost.
3. **Refusal audit rows name an attacker-chosen account as the actor.** `registration.ts:400`/`:520` pass `existing?.auditToken` even for IP-scope refusals, and `identity.ts:104-105` writes it to both `actor_key_ref` and `target_id`. ## 4. NEW TICKETS RECOMMENDED

- **T1 â Move argon2id off the request thread** (worker pool) plus a bounded per-IP KDF cache. Larger: touches the crypto package API, API boot, and the DB layer. Justification: ~200 ms of whole-API freeze per registration, a ~5 req/s process ceiling, and ~220-1200 source IPs saturating the product. Also the only way to afford genuinely ASIC-hostile KDF parameters if V wants them.
- **T2 â Real client IP, done safely.** Nothing sets `trustProxy`, so `request.ip` is the socket peer. Behind any proxy every audit row gets the same constant hash and the whole internet shares one bucket â which would make VR-7's per-request cost buy nothing. Must be ticketed rather than folded in because the naive fix is dangerous: `apps/ui/app/api/[...path]/route.ts` blanket-copies client headers, so `trustProxy: true` would put `request.ip` under caller control. Needs a pinned hop + an XFF allowlist in the UI proxy. Latent today (no UI calls `/v1/auth/*` yet).
- **T3 â Graceful shutdown with an audit drain.** `main.ts` ends at `await api.listen(...)`; every deploy silently discards up to 60 s of refusal aggregates and all in-flight verification mail. Note in the ticket that the obvious fix is wrong: `drainRateLimitAuditFlushes` waits on an `unref()`'d timer up to 60 s out that, in an idle loop, never fires â the handler needs a synchronous force-finalize-and-write.
- **T4 â Refusal-audit forensics.** Distinct-source cardinality (bounded HLL or capped source-hash set) plus stopping the attacker-chosen actor token on IP-scope refusals. Ticketed rather than folded because V should first rule on what a refusal row is *for*.
- **T5 â Add `UserDekStore.destroy()` to the S10 packet now**, while the interface is cheap to change, rather than discovering at S10 that the shred ceremony has no API to call.
