## The spike's answer, verbatim

**Path: spike** — you asked a feasibility question, so I did read-only research and I'm reporting an answer, not writing code.

## Short answer

Yes, and you're most of the way there already. The provider layer is **environment-agnostic by construction**: every provider is `openai-compatible-http` reduced to `{base_url, model, authorization_header?}`. Localhost already points those at loopback CLI relays; a VPS just points the same shape at real API endpoints with a `Bearer` key. **No change to the call path is needed.**

## What's actually there

**The transport is uniform.** [packages/providers/src/index.ts:338](dialectical-engine/packages/providers/src/index.ts:338) does `POST ${baseUrl}/chat/completions` and sets `authorization` only when `authorizationHeader` is present. `normalizedProviderBaseUrl` accepts any `http(s)` URL ending in `/v1` — so `http://127.0.0.1:8792/v1` and `https://api.x.ai/v1` are both already legal. OpenAI, xAI and Anthropic all expose an OpenAI-compatible `/v1/chat/completions`, so all three roster makers work through the existing adapter with nothing but a key.

**The local side is the CLI relays.** [apps/runner/src/dev-provider-panel.ts:26](dialectical-engine/apps/runner/src/dev-provider-panel.ts:26) defines five loopback slots (`development:codex-cli` :8791, `codex-premium` :8795, `claude-cli` :8792, `claude-premium` :8796, `grok-cli` :8793). Each is an OpenAI-compatible server wrapping your subscription CLI — [acceptance/claude-relay.ts:26](dialectical-engine/acceptance/claude-relay.ts:26) shells out to `/Users/vladmihaimiron/.local/bin/claude`, [acceptance/model-shim.ts:15](dialectical-engine/acceptance/model-shim.ts:15) to the ChatGPT.app-bundled `codex`. Hardcoded Mac absolute paths — these physically cannot run on a VPS, which is fine: that's the whole point of the split.

**Selection is config, not code.** Both `apps/api` and `apps/runner` read `PROVIDER_DISCOVERY_TARGETS_JSON` from env and cross-check it against a `configuredProviderSet` register row read from **the deployment's own Postgres** ([packages/critique/src/index.ts:245](dialectical-engine/packages/critique/src/index.ts:245)). `parseProviderDiscoveryTargets` enforces **exact set equality** on `provider_ref` between the two — mismatch throws `PROVIDER_DISCOVERY_TARGET_SET_MISMATCH`. So each deployment already has two independent knobs: its DB register publication and its env JSON.

**There is no environment switch today.** No `DEPLOYMENT_KIND`, no hostname sniffing, no localhost check anywhere in `apps/` or `packages/`. Only `NODE_ENV` and a `deploymentRiskTier` register row. And `deploy/` contains only the dev auth stack and the observation agent — **there is no VPS deployment path yet at all**.

## The one real design decision

Since the provider_ref set must match the DB register exactly, you pick one of two shapes:

- **A — same refs, different targets.** Keep the published set, swap only the env JSON's `base_url` + `authorization_header`. Zero code, zero migration. Cost: your refs are literally named `development:claude-cli` on a production box, which will lie in every ledger row and audit trail.
- **B — a production roster.** Publish a second provider set (`production:anthropic-api`, etc.) on the VPS's own database via the existing publish path ([apps/runner/src/dev-provider-set-publish-cli.ts](dialectical-engine/apps/runner/src/dev-provider-set-publish-cli.ts), generalized out of `dev-`). Honest refs, honest lineage. Cost: a small amount of real work — a prod roster module plus a publish CLI that isn't dev-gated.

**I'd recommend B.** Your ledger records `providerRef`/`maker`/`model` for auditability, and the whole register design is built on "config is declared and sealed, not inferred." A `development:` ref serving paid API traffic corrupts exactly the property that machinery exists to protect.

## Where the switch should live — and where it shouldn't

Put it at **process launch** (which env file / which register publication the box boots with), **not** as a runtime `if (hostname === 'localhost')` inside the API. Runtime sniffing would put "am I local?" into the request path, defeat the sealed-register invariant, and make a run's provider lineage depend on ambient machine state instead of declared config. The launcher already works this way — `dev-auth-stack` composes the dev env; a VPS launcher composes the prod one.

## Two things to flag before you build

1. **Secrets.** API keys would sit in plaintext inside `PROVIDER_DISCOVERY_TARGETS_JSON` in the process env. The repo already prefers file-backed secrets everywhere else (`KEK_PATH`, `AUDIT_KEY_STORE_PATH`, `dev-secret-files-cli`). A `PROVIDER_DISCOVERY_TARGETS_PATH` variant would match the house style — it's a small addition, but it's an addition.
2. **Discovery probes cost money on the VPS.** [apps/api/src/provider-discovery.ts:47](dialectical-engine/apps/api/src/provider-discovery.ts:47) sends a real 8-token completion per provider to health-check it, cached by `probeFreshnessMs`. Free against a local CLI relay; billed against real endpoints. Trivial in absolute terms, but check that `probeFreshnessMs` isn't set aggressively low.
