## Verified-OK controls
- **Ownership enforced in the repository query on every `{id}`/`{nodeId}` route (no IDOR, opaque 404).** Every serve/db read used by the API gates on `core.run_is_owned_by(run,ownerRef,legacyAskerId)` inside the SQL — `readAnswerProjection` (`packages/serve/src/index.ts:1359-1420`), `readRunAnswerProjection` (1770-1779), `readInspectionProjection` (1918-1969), `readNodeProjection` (1971-1984), `readExecutionLedgerDigest` (1845-1866), `readLoadingProjection` (`packages/db/src/index.ts:1280-1330`), SSE `events` (`index.ts:1402-1437`, re-validated after the ungated lifecycle projection), `recordInvestigationRequest` (`serve:1782-1844`, ownership re-checked under `FOR UPDATE` before the write), `unlinkForAnswer`, publication `readOwnedVisibility`/`readAuthorPseudonym` (`packages/db/src/publication.ts:406-449`). Predicate itself is latest-owner-wins and requires an active user (`migrations/0037_run_ownership.sql:289-327`). Foreign/guessed ids return `null`→resource-specific 404 (`ANSWER_NOT_FOUND`, `NODE_NOT_FOUND`, `RUN_NOT_FOUND`…); no 403 existence leak. Matches `tests/unit/s7-authorization.test.ts`.
- **Deny-default route policy.** `onRoute` hook refuses to register any route whose method+url is absent from `authorizationPolicyInventory` or whose declared `auth`/`origin` disagree (`index.ts:339-348`); `preHandler` rejects any `auth` value that is not exactly `public|user|operator` (`index.ts:396-398`). `s07-contract`/`s7-authorization` pin it.
- **Operator routes are entirely unreachable by any cookie session.** After cookie auth, `authPolicy==="operator"` → unconditional `403 OPERATOR_REQUIRED` (`index.ts:432-434`); no operator session is issued anywhere (IMPLEMENTATION-STATUS P1-S7). `GET /v1/deployment`, `GET /v1/dev/evaluator`, `POST /v1/dev/evaluator/consumer-selection` therefore always 403; the evaluator routes are also only mounted when `evaluatorDevMenu` is provided (dev-only, `NODE_ENV=development` gated in the env parser).
- **CSRF: double-submit + exact Origin + hashed compare, fail-closed when unconfigured.** Mutating methods (`POST/PUT/PATCH/DELETE`, `index.ts:172`) require `exactOrigin(origin, allowedOrigin)` **and** `exactCsrfPair` (43-char grammar + `timingSafeEqual`, `index.ts:297-303`) **and** `sessions.verifyCsrf` (SHA-256 hash compare vs the session's stored csrf hash, `sessions.ts:264-267`) (`index.ts:422-430`). `exactOrigin(x, undefined)` returns **false** (`index.ts:292-295`) → probed: with `allowedOrigin` unset, login and every cookie mutation return `403 CSRF_VALIDATION_FAILED` (fails closed, never open). `GET/HEAD/OPTIONS` are exempt (safe methods; HEAD/OPTIONS 404 anyway). The trusted-origin public route `POST /v1/auth/login` enforces exact Origin with no token (correct — no ambient credential pre-login). CSRF cookie is deliberately non-HttpOnly (`index.ts:309-311`) so the SPA can echo it — correct double-submit pattern.
- **Session tokens: 256-bit, SHA-256 at rest, useless if the DB hash table leaks.** session/csrf/challenge/grant/verification tokens are `randomBytes(32).toString("base64url")` (43 chars, `crypto:1039-1041`), stored only as `sha256:<hex>` (`hashVerificationToken`, `crypto:1043-1048`; column `CHECK ~ '^sha256:...'`, `migrations/0036_sessions.sql:6-7`). Browser-visible values never enter DB/audit/logs/URLs. Idle 14 d / absolute 90 d (`session-policy.ts:54-56`), idle slid to `LEAST(absolute, now+idle)` and both checked on every auth (`authenticate_session_t9`, `migrations/0040:3007-3046`).
- **Rotation, revocation, no fixation, logout clearing.** login mints fresh session+csrf (`sessions.ts:313-333,378-447`); step-up rotates both (`rotate_session_after_step_up`, `migrations/0040:3443-3540`, single-use MFA step-monotonicity + `FOR UPDATE`); no pre-login cookie is ever promoted; logout/revoke/revoke-all set `revoked_at` and clear cookies (`index.ts:521-549`, `sessions.ts:453-488`). `s5-session-http` pins the lifecycle.
- **Step-up grants are action- and target-bound, time-boxed, single-use, session-bound.** `step_up_grant` rows carry `(token_hash, session_id, user_id, action, target_run_id | target_account_id, expires_at≤now+5 min, consumed_at)` (`migrations/0039:10-25`, `0040:3527-3538`); liveness/consumption re-checks all of these under the run/account lock and sets `consumed_at` (`publication_grant_is_live` `0039:152-190`; publish/unpublish consume `0040:4088-4089,4527-4528`; erasure consume `0040:5044-5051`). A fresh cookie session cannot skip step-up: `preflightGrant`/`schedule` require the grant to match the *current* `session_id`. `s8-publication-http`/`s10-erasure-http` pin it.
- **Enumeration/timing floors.** register (`holdRegistrationEnumerationClamp` 500+100 ms + admission-gate-before-work + dummy hash on duplicate, `registration.ts:673-678,1461`), resend/recovery (`holdEnumerationFloor` 500 ms, `registration.ts:667-671`, `recovery.ts:88-91`), login (dummy `dummyPasswordHash` on unknown email = equal Argon2 work, `sessions.ts:283-287`), generic public responses (`REGISTRATION_PUBLIC_RESPONSE`, `RESEND_PUBLIC_RESPONSE`, `RECOVERY_START_PUBLIC_RESPONSE`). Legacy claim path requires cookie+CSRF+`legacy_token`, hashes to `asker:sha256(token)`, claims only event-less runs, fully audited (`migrations/0041:95-200`). `s9-dev-token-retirement-http` pins it.

Read-only; no mutation route reaches it.

## B5 — maximum legitimate request-body size per route (for the limit constants)
- **Credential/token/management routes** (register, verify-email, resend-verification, login, logout, step-up, mfa/*, recovery/start, DELETE /v1/account, account/erasure/cancel, legacy-runs/claim, DELETE /v1/debates/{id}, publish, unpublish): largest legitimate field is `legacy_token ≤ 1024 bytes` (legacy-runs/claim) → ~1.1 KiB; everything else is emails (≤320), 43-char tokens, and short literals → < 1 KiB. **`AUTH_BODY_LIMIT_BYTES = 16_384` (16 KiB) is safe** for all of these with wide margin. Recommend also applying it to publish/unpublish/step-up/erasure/legacy-claim (currently they would inherit the 256 KiB server default), since none carries free text.
- **Free-text routes**: `POST /v1/asks` (`question_line` + `steering_annotations` + `depth_params` all unbounded in the contract; probe accepted a 900 KB question_line) and `POST /v1/answers/{id}/investigations/{gapRef}` (`user_input` free text). Realistic worst case is tens of KiB. **`API_BODY_LIMIT_BYTES = 262_144` (256 KiB) server default is safe**; no route legitimately needs more. (256 KiB is a reduction from the current 1 MiB Fastify default.)
- **GET routes**: bodyless.
- Caveat: `password` has **no maximum length** in `passwordPolicy` (`auth-policy.ts:385-394`, only `minimum_length:8`); a 16 KiB password is still hashed by Argon2 (negligible vs the 64 MiB memory cost) but adding a max (e.g. 1024) is cheap defense. `maxParamLength` currently defaults to **100** (probed); B5's proposed `128` is a slight loosening — fine, but validate `gapRef` explicitly (L1-F7) rather than lean on it.

## B10 — is there any per-user admission/spend control for asks?
**No.** `POST /v1/asks` has no rate or spend limiter (`index.ts:863-874`). `withOwnerAskAdmissionLease` (`packages/db/src/index.ts:898-925`) is a per-owner `pg_advisory_lock` that *serializes* concurrent asks — it is mutual exclusion, not throttling, so an authenticated user can submit unlimited asks sequentially, each fanning out to paid model CLIs. The only related bound, `MAX_OWNER_PRIVATE_HISTORY_SCAN = 128`, caps the *live-run comparison window* (liveness/memory), not submission rate, and throws only once ~128 live private runs exist. B10 is required. Anonymous `GET /v1/public/*` likewise has no limiter (L1-F2).

## Out-of-scope observations
- **R2 / cross-lane L3+L7 (production-critical for the VPS):** today `hardenIncomingProxyHeaders` (`apps/ui/trusted-client-ip.mjs:28-41`, `server.mjs:21,29`) drops **all** inbound forwarded headers, and the API trusts only loopback (`apps/api/src/client-ip.ts:9-12`). On a VPS behind a TLS-terminating reverse proxy this makes the API see **every** caller as `127.0.0.1`, collapsing all per-source auth limiters (register/verify/resend/login/mfa) and the proposed B10 public-read limiter into one shared bucket — either one attacker exhausts the shared budget and locks out everyone, or throttling is meaningless. Plan Task **C2** (explicit `DIALECTICAL_UI_TRUSTED_PROXIES`) is the fix and must land before any per-source limiter is trusted in production. The API's own `trustProxy` should stay loopback (Next remains the only hop). Flagging because it directly undermines L1 controls.
- **R2 cookies/Origin behind the proxy:** `__Host-` prefix + `Secure` + `SameSite=Lax` (`index.ts:305-311`) require the browser origin to be HTTPS and `PUBLIC_APP_URL` to equal that exact public origin (scheme+host, `runtime-environment.ts:95`). Correct as long as the proxy terminates TLS at the same public origin. `SameSite=Lax` (not Strict) is acceptable given the Origin+double-submit CSRF stack.
- **Session binding is weak (defense-in-depth only):** binding hash is `HMAC(bindingKey, "…user-agent:v1\0"+UA[:256])` (`sessions.ts:200-206`); UA is attacker-known/spoofable, so a stolen cookie replayed with the victim's UA passes. Also `bindingKey` defaults to the **blind-index key** because `SessionService.create` is called without `bindingKey` (`sessions.ts:182-184`, `main.ts:215-225`) — domain-separated by the HMAC prefix, so not exploitable, but it is key reuse across two purposes; worth an explicit dedicated key.
- **L2:** token/hash primitives (`randomBytes`, SHA-256 at rest, Argon2id 64 MiB/t3 password, 19 456 KiB/t2 audit-IP KDF) and the Argon2 pool bounds (2 workers, 32/96/128 lane caps, 10 s job timeout, `packages/crypto/src/argon2-worker-pool.ts:131-145`) are L2's to grade; noted here only as inputs. The `AuditContextHasher` in-flight cache is bounded (4096 entries / 60 s TTL, `crypto:849-852`).
- **L5:** all identity/session/publication mutations go through `SECURITY DEFINER` functions with `SET search_path=pg_catalog` and per-capability `REVOKE`s from `PUBLIC`/runtime roles (`migrations/0040:6172-6210`); runtime holds only operation-specific wrappers. Parameterization is total (no string-built SQL on the L1 paths). L5 owns the full principal/RLS grading.
