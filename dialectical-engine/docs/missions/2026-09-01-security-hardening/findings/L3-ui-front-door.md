## Verified-OK controls
- XSS sinks: the only `dangerouslySetInnerHTML` is the static, app-owned theme bootstrap (`app/layout.tsx:36-42`) which reads `localStorage['debateai.mode']` and assigns `dataset.mode` only on strict equality with two literals; no `innerHTML`, `eval`, `javascript:` or `createObjectURL` anywhere in `apps/ui` (repo grep). Export links are `data:application/json;charset=utf-8,` + `encodeURIComponent(JSON)` with a `download` attribute (`lib/v3/answerExport.ts:87-88`, `lib/v3/publicAnswerExport.ts:19-20`, `DebatePageClient.tsx:1160,1191`, `AnswerHonestyDrawer.tsx:469`) — not `text/html`, so no XSS-on-open. Every other `href` is a literal or a same-origin path built from ids (`DebatesBuffer.tsx:72,100` with `encodeURIComponent` for `public_ref`; `PublicationControl.tsx:139`; `TopBar.tsx:45` receives only `/`); model-produced text reaches the DOM only as React text nodes or `title` attributes (`DebatePageClient.tsx:1104-1107,1640-1680`).
- Open redirect: `lib/returnPath.ts:7-16` allow-lists `/new`, `/`, `/settings`, `/public/debate/<uuid>`, refuses `//`, `/\`, any backslash, and only ever returns a leading-slash path; used by `LoginFlow.tsx:34-37`; cross-links encode `next` (`LoginFlow.tsx:58`, `SignUpFlow.tsx:57`); `AuthGate.tsx:22` and `SessionControls.tsx:74-76` navigate to constants; `/new?topic=` only seeds React state (`app/new/page.tsx:66`). `authNavigationGuard.ts` is a UI flag store, not a redirect path.
- Browser storage: only `debateai.mode` (`components/ModeToggle.tsx:21`, `app/layout.tsx:39`); no `sessionStorage`; the session is an HttpOnly `__Host-` cookie; the CSRF cookie is intentionally readable for double-submit (`lib/api.ts:293-297`, `client.ts:177`); `components/authRoutes.source-test.mjs:37,48` pins the absence of `localStorage|sessionStorage|Bearer` in the auth flows.
- Client API base: `lib/api.ts:40-70` refuses backslashes, `//`, `?`/`#`, dot segments and proves same-origin by round-tripping through a sentinel origin; `createSameOriginFetch` keeps only `pathname+search` (`:88-90`) and refuses `Request` inputs (`:83-87`); no client-side secret exists (`NEXT_PUBLIC_*` are flags; `apps/ui/.env.local` holds `/api` and a loopback API base).
- Proxy request side (`route.ts:9-23,69-99`): exact header allowlist (drops `authorization`, `host`, `x-forwarded-*`, the retired dev header), cookie grammar `^[A-Za-z0-9_-]{43}$` with duplicate → drop-all, CR/LF/NUL refusal, path segments re-encoded (`:62`), query passed verbatim, `x-forwarded-for` only from the edge-stamped header; `lib/sessionProxy.test.mjs` pins this.
- Proxy response side (`route.ts:24-35,101-132`): allowlist drops CORS and internal headers; `Set-Cookie` accepted only in the exact ruled grammar (name, value, `Path=/`, `Max-Age`, `HttpOnly`/`Secure`, `SameSite=Lax`, or the exact clearing form); 204/205/304 and HEAD send no body (`:158`); `text/event-stream` and `cache-control` pass so SSE works; the 502 envelope states only the proxy fact (`:151-154`); `OPTIONS`/`HEAD` are explicit exports (`:171-173,191-193`), other methods get Next's 405.
- Edge header hygiene: `hardenIncomingProxyHeaders` runs for both request and upgrade paths (`server.mjs:21,29`), removes `forwarded`, `x-real-ip`, `cf-connecting-ip`, `true-client-ip`, every `x-forwarded-*` and the trusted header itself; Node lowercases keys and joins duplicate lines, so case and multi-line variants cannot bypass it; Next only re-synthesises `x-forwarded-{host,port,proto,for}` from `Host`/socket (`base-server.js:562-568`); no code in the UI or API reads any other client-IP header name, and the proxy allowlist is the real guarantee towards the API.
- Error handling: `server.mjs:22-26` logs server-side and returns plain `INTERNAL_SERVER_ERROR`; no custom `error.tsx`/`global-error.tsx`, so production uses Next's stack-free defaults; the dev overlay exists only under `--dev`. `next.config.mjs:36-44` only adds extension aliases.
- Source maps: `productionBrowserSourceMaps` is unset (default `false`) and no server source maps are enabled — asserted from Next defaults; no build output was inspected (none exists in the worktree).
- Production gating: `/admin/workers` is a static refusal screen issuing no request (`app/admin/workers/page.tsx:3-22`); `EvaluatorDevMenu` is imported only by `OperatorSettingsScreen`, which nothing renders (`app/settings/page.tsx:37-39,87,229`), and is additionally gated by `NODE_ENV !== "production" && NEXT_PUBLIC_EVALUATOR_DEV_MENU_ENABLED === "true"` (`:14-15`, build-time inlined); its API routes `/v1/dev/evaluator*` are L1's to gate.
- Security headers on every path including the live 404 (`next.config.mjs:22-34`; `tests/integration/s5-ui-security-smoke.mjs:22-34,89-91`); HSTS, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, restrictive `Permissions-Policy`, `Cache-Control: no-store`.
- MFA enrolment surface: otpauth URI and Base32 secret validated before use (`lib/mfaEnrollment.ts:88-92`); QR rendered locally as an SVG path of booleans (`app/enroll-mfa/page.tsx:46-59`, `lib/totpQr.ts:208-214`) — no third-party QR service; the bearer leaves the address bar before the first await (`mfaEnrollment.ts:67-77`); the page has no native `<form>` (`authRoutes.source-test.mjs:173-178`); the TOTP secret is never redisplayed after proof (`enroll-mfa/page.tsx:125,226`).
- Auth forms: POST with query-free same-origin `action`s (`authRoutes.source-test.mjs:159-171`); stable public copy instead of exception text (`:131-140`); recovery-code custody blocks only home navigation (`:180-187`).
- Dev observability logger is server-only, redacts secret-shaped keys and values (`lib/observability/logger.ts:83-86,88-155`), writes only under an operator-chosen path, and currently has no importer.

## B9 nonce-CSP feasibility
**Verdict: YES** — a per-request nonce with `'strict-dynamic'` works on Next 15.5.23 App Router behind the custom `server.mjs`, in both `node server.mjs` (production) and `node server.mjs --dev`, with the mechanism below and six corrections to the task as written.

Mechanism (all citations `apps/ui/node_modules/next/dist/...`):
1. Middleware runs inside the router-server that `next()` uses for custom servers: `resolve-routes.js:308-333` invokes it for every matched request, then applies its request-header rewrites — `NextResponse.next({ request: { headers } })` becomes `x-middleware-override-headers` + `x-middleware-request-<name>` and is copied into `req.headers` (`resolve-routes.js:378-400`). Its response headers (the CSP) are merged into the final response.
2. Next discovers the nonce from the **request** header `content-security-policy` (or `…-report-only`): `app-render.js:108-109` → `getScriptNonceFromHeader` (regex `'nonce-([A-Za-z0-9+/_-]+={0,2})'`, `get-script-nonce-from-header.js:11`), threads it through `App`/`ErrorApp` (`:765,801`), the bootstrap `<script src>` tags (`getRequiredScripts(…, nonce, …)`, `:1242`), the inline flight-data scripts `self.__next_f.push` (`createInlinedDataReadableStream(…, nonce, …)`, `:1298,1327`) and server-inserted metadata (`:1231`). Webpack chunk loading uses `document.createElement('script')`, which `'strict-dynamic'` permits; `next/font` emits only `<link>`; `style-src` keeps `'unsafe-inline'` for React style attributes. The app's own inline script gets `nonce={nonce}` as in the plan.
3. `headers()` in the root layout makes every route dynamically rendered, so no prerendered HTML can carry a stale nonce; this includes `/_not-found`, so the smoke's live-404 check still sees a fresh nonce.
4. `next dev` follows the same `app-render` path (HMR/refresh/dev-overlay scripts are emitted with the nonce) and needs `'unsafe-eval'` for eval source maps — the plan already varies `script-src` by `NODE_ENV`. Verify once in the Browser pane as Step 3 says.
5. Middleware runs in the in-process edge sandbox; `crypto.getRandomValues` is native Web Crypto there. `Buffer` is only a webpack ProvidePlugin polyfill in that bundle (`webpack-config.js:1603-1608`).

Corrections to the task as written:
- **C-1 `/api/*` loses its CSP.** The plan's sentence "`/api/*` keeps the API's own CSP" is false: `route.ts:24-35` never forwards `content-security-policy`; today `/api/*` gets the UI policy from `headers()` `source: "/:path*"`; with the static entry removed and the matcher excluding `api/`, proxied JSON would have none. Keep a second `headers()` entry for `/api/:path*` with `default-src 'none'; frame-ancestors 'none'` (or add the header to the response allowlist).
- **C-2 Fail-closed fallback.** Pre-set today's static policy in `server.mjs` on every response before `handle()`; the middleware's `set` overrides it on matched HTML routes, and anything the middleware does not touch still carries a CSP. Smoke-assert a CSP on `/`, on `/api/v1/session`, and on a matcher-excluded 404.
- **C-3 Only the middleware may name the nonce.** Strip client-supplied `content-security-policy`, `content-security-policy-report-only`, `x-nonce` and `x-middleware-*` request headers in `hardenIncomingProxyHeaders` (the middleware's `set` already wins, but the edge should not rely on it). CVE-2025-29927's `x-middleware-subrequest` bypass is fixed since 15.2.3 and the string no longer exists in 15.5.23's dist; with C-2 a bypass would only revert to today's policy anyway.
- **C-4 Nonce encoding.** Use `btoa(String.fromCharCode(...crypto.getRandomValues(new Uint8Array(16))))` (Web APIs only, 24 chars, matches both Next's regex and the smoke's `[A-Za-z0-9+/=]{22,}`) instead of `Buffer`.
- **C-5 Build gate.** `scripts/assert-auth-front-door-routes.mjs:20,29-32` (run by `apps/ui` `build`) requires `/login`, `/sign-up`, `/verify-email`, `/enroll-mfa` in `routes-manifest.json` `staticRoutes`; that list is keyed by path shape (no dynamic segments), not by prerender status, so making them dynamic keeps the gate green — confirm the `AUTH_PRODUCTION_ROUTES_VERIFIED` line at Step 3 and say so in the commit body.

## C2 reverse-proxy review
**Premise confirmed:** with today's code every client behind a TLS-terminating Caddy/nginx is `127.0.0.1` end-to-end (L3-F11 trace), so per-source limits and the audit source IP collapse. **Design verdict: correct, ship it with the amendments below.**

- **Last-hop selection is right for both real proxies.** Caddy 2.5+ overwrites `X-Forwarded-For` with the client address unless `trusted_proxies` says otherwise (single hop → last = client); nginx's `$proxy_add_x_forwarded_for` appends the observed address (last = the trusted hop's observation). Taking the rightmost hop and trusting exactly the immediate peer is the only rule that cannot be spoofed by a client-supplied prefix. Pin in C3: Caddy without `trusted_proxies` (or loopback only); nginx `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`.
- **Empty list = today's behaviour.** `trustedProxies.includes(socketIp)` is false → socket address; no header is ever honoured. Fail-closed by default.
- **IPv4-mapped IPv6.** Both sides pass through `normalizeClientIp` (`trusted-client-ip.mjs:13-22`): `::ffff:127.0.0.1` and `::ffff:7f00:1` normalise to `127.0.0.1`, so a dual-stack listener (`DIALECTICAL_UI_HOST=::`) reporting the mapped form still matches a `127.0.0.1` entry. Set the unit to `DIALECTICAL_UI_TRUSTED_PROXIES=127.0.0.1,::1` anyway: a `localhost` upstream may resolve to `::1`, and an unlisted `::1` silently collapses (not spoofs) attribution.
- **Caps.** The 512-char header cap and the 64-char per-literal cap are adequate; add a hop-count cap (e.g. 8) so a 512-byte header of commas does bounded work, and document that `ip:port` (IIS/ARR) and bracketed IPv6 forms fail normalisation and fall back to the socket address (safe, not spoofable). Zone ids (`%`) are already refused.
- **Capture before strip.** The snippet reads `headers["x-forwarded-for"]` before the deletion loop — keep that order; Node has already lowercased and comma-joined duplicate lines, so `"a, b"` splits correctly. Empty/trailing hops (`"1.2.3.4, "`) normalise to `null` → socket fallback.
- **`parseTrustedProxies` grammar.** The interface text says whitespace-only input is refused, the snippet returns `[]` for it; choose the fail-closed reading (undefined/empty string → `[]`; whitespace-only or any unparsable entry → throw). House style asks for `TypeError` with a `code`; `server.mjs:13` currently throws a plain `Error`, align both at the same touch.
- **Proto is still discarded.** `x-forwarded-proto` remains stripped, so Next synthesises `http` behind TLS (`base-server.js:565-567`). Nothing consumes it today (cookie `Secure` is set unconditionally by the API and enforced by `lawfulSetCookie`; no absolute-URL generation; no Server Actions), so this is safe; optionally accept `x-forwarded-proto` only when the peer is trusted and the value is exactly `https`.
- **API side unchanged — confirmed.** `TRUSTED_UI_PROXY_NETWORKS` (`apps/api/src/client-ip.ts:9-12`, `index.ts:336`) must stay loopback: Next is still the API's only peer and forwards a single normalised literal, so Fastify's right-to-left walk yields the client directly. Widening it would let anything on the box speak for any client.
- **Both edge paths.** Pass `trustedProxies` to the upgrade-path call too (`server.mjs:29`) as the plan says — and fold L3-F2 (destroy production upgrades) and L3-F1 (body cap) into the same `server.mjs`/`route.ts` change to avoid three merges on one file.
- **Tests to add to the plan's four:** mapped-IPv6 trusted remote; trailing empty hop → socket; two header lines joined by Node → last; hop count over the cap → socket; whitespace-only env → throws (if adopted); the API-side contract test that `x-forwarded-for` received from the UI is a single literal.
