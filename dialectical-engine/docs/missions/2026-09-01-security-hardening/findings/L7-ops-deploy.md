### C2 (explicit reverse-proxy trust for the UI edge) — design review
- Current behaviour confirmed: `hardenIncomingProxyHeaders` deletes every forwarded/real-IP header and stamps `x-debateai-client-ip` from the socket peer (`apps/ui/trusted-client-ip.mjs:28-42`; called at `server.mjs:21,29`); the API trusts only loopback proxies (`apps/api/src/index.ts:336`) and derives `request.ip` (`:360`). C2's "every client would be 127.0.0.1 behind Caddy" diagnosis is right.
- Gap 1 (design): `DIALECTICAL_UI_TRUSTED_PROXIES=127.0.0.1` is not an *exact proxy identity* — every local process on the VPS shares that source address. Anything that can open `127.0.0.1:3001` (a compromised runner or vendor CLI, any other unit) can forge `X-Forwarded-For` and thereby evade per-IP admission limits (B5/B10) and poison the audit source IP (asset 1.1.5). The same is true one hop later at the API (`TRUSTED_UI_PROXY_NETWORKS`). Recommended floor: Caddy → UI over a Unix socket (`reverse_proxy unix//run/debateai/ui.sock`; Node `server.listen({ path })`, socket 0660 owned `debateai-ui:caddy`) so trust is filesystem-enforced and no `trustedProxies` list is needed; second-best: Caddy `header_up X-Debateai-Edge {env.DEBATEAI_EDGE_SECRET}` verified with `timingSafeEqual` before honouring XFF. Same pattern UI → API (Unix socket, or keep loopback and bind the API's listener to a socket path in C1).
- Gap 2 (invariant): "last XFF hop wins" is correct only while Caddy's `trusted_proxies` stays unset (Caddy ≥ 2.5 then replaces client-supplied XFF with the peer IP). Pin `Caddyfile` must not contain `trusted_proxies` in the C3 test, and document it next to the env var.
- Gap 3 (minor): the stripping loop also drops `x-forwarded-proto`; with Caddy in front, forward proto only from the trusted hop or rely on `PUBLIC_APP_URL` (the API already does). Not security-relevant today.
- The parser rules (`parseTrustedProxies`: exact literals, refuse CIDR/hostnames, 512-byte XFF cap) are sound.
