## Verified-OK controls
- AEAD: AES-256-GCM, 96-bit nonce from `randomBytes` per call, 128-bit tag, AAD = `JSON.stringify([1, keyId, aad7])` binding schema, table, primary key, run id, owner ref, key id and envelope version — index.ts:46-58, 249-252, 265-289; decrypt rejects `v !== 1`, `keyId !== aad[5]`, non-canonical base64, wrong nonce/tag length and maps every failure to `CRYPTO_AUTHENTICATION_FAILED` — index.ts:254-259, 291-316. Envelope downgrade: only `v: 1` exists and the version is inside the AAD, so an altered `v` fails authentication. Nonce reuse under concurrency: no counter state, CSPRNG per call; per-key usage counts are small (KEK wraps one DEK per user, a user DEK wraps one key per run plus the TOTP seed, a run key encrypts the rows of one run), far below the 2^32 random-IV guidance; the code names the GCM-SIV/XChaCha residual (index.ts:276-278). Key commitment: AES-GCM is not key-committing, but every key is 256 random bits held in custody and the key id is authenticated, so no partitioning-oracle surface exists (INFO).
- KEK wrap/unwrap: `wrapDek`/`unwrapDek` = AEAD under the KEK with the same 7-tuple AAD; unwrapped length pinned to 32 — index.ts:345-366. ## Out-of-scope observations
- C3 must state the key file contract explicitly: raw 32 bytes (`head -c 32 /dev/urandom > kek.bin`), because `copyKey` rejects hex/base64 encodings (65/45 bytes) with an opaque `KEK_UNRESOLVED` (index.ts:142-149, 326-329); files must be owned by the service user (`User=debateai`) with mode 0600 in a 0700 directory — a root-owned 0600 file is unreadable by the service, and `EnvironmentFile` semantics (read by root) do not carry over to key files; `ReadWritePaths=` must include `USER_DEK_STORE_PATH` and `PUBLICATION_KEY_STORE_PATH` because the API creates directories there at runtime (index.ts:1169-1173).
- L5: `core.run_content_attestation_secret` (0040:111-118) is a DB-resident MAC key derived from the run key; the attestation is forgeable by anyone who can read that table, so confirm no default privilege or future `GRANT … ALL TABLES` reaches it for runtime principals (0000:301 predates the table).
- L5: `identity.audit_event.actor_ciphertext` is inserted as `NULL` by the SQL appender (0040:1720-1723) and `AUDIT_KEY_STORE_PATH`/`audit-keys/` is created, custody-checked and never read or written (main.ts:79 only) — dead custody configuration; decide whether per-user actor keys are still a design goal.
- L5/L7: `ALTER ROLE … PASSWORD` statements for the 10 dev principals go through `format()` SQL (dev-database-principals.ts:276-305); PostgreSQL does not redact them from `log_statement`/`log_min_duration_statement` output — C3's Postgres hardening should set `log_statement='none'` around provisioning (the production provisioning command likely has the same shape).
- L7: `dev-auth-data-plane.ts:10` carries a default superuser URL with the literal password `debateai-dev-only`; the API child inherits stderr (`stdio: ["ignore","ignore","inherit"]`, dev-api-process.ts:342) — check Fastify error logs never echo request headers/cookies (L1/L7).
- L7/B4: `.local` itself is created 0700 by `generate-secrets` but only required to be uid-owned there (dev-secret-files.ts:191), while the three later launchers require exactly 0700 (dev-hatchet-token.ts:206, dev-api-environment.ts:327, dev-api-process.ts:65) — a pre-existing 0755 `.local` passes step 1 and fails step 3 with an unrelated-looking code.
- Orchestrator: the Hatchet dev token is a one-year ES256 JWT with `tls_strategy: "none"` (dev-hatchet-token.ts:21-24, 394-401); fine on loopback, but C3 must not reuse the dev path (token file under custody, TLS on for the VPS).
