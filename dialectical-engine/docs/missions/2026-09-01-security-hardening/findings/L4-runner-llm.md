Conclusion: the Phase-4 "instruction/data separation" claim (IMPLEMENTATION-STATUS Phase 4, third bullet) holds for the relay transport and for `review`, not for the runner's expansion legs.
- **Q2 Output parsing.** `JSON.parse` sites on model/provider text: packages/providers/src/index.ts:294 (`contentParseStatus`, classification only) and 350 (whole HTTP body, no size cap → L4-F3); packages/judgement/src/s04.ts:143/146/150 (up to three strategies: raw, one fence, first brace-balanced object; regex at 144 is anchored/lazy and linear; the brace scanner 111-133 is O(n)); apps/runner/src/index.ts:869/878. Verified OK apart from the size caps.
- **Q3 Base URL and credentials.** `normalizedProviderBaseUrl` (providers:109-132): `http:`/`https:` only, no userinfo/query/hash, path must end in `/v1`, no host/port/IP-range restriction → L4-F7. `authorizationHeader` is used only as the `authorization` request header (providers:333-336; provider-discovery.ts:44-47); it is not in raw-artifact metadata (providers:386-390), not in ledger rows, not in `core.provider_probe` (`record_provider_probe(uuid,text,text,text,text,text,timestamptz)` migrations/0048_provider_probe_capability.sql:1-35; `ProviderProbeRecord` fields at provider-discovery.ts:80-88; discovered panel members carry `provider_ref/maker/model_id/probe_evidence_ref/probed_at`, 145-151), and no `console.*` exists on the runner path (grep of main.ts, index.ts, providers, judgement). - **Q4 Ceilings, deadlines, retries, worst-case spend.** Per HTTP attempt: `max_tokens = tokenCeiling` is only a request hint (providers:343) and `AbortSignal.timeout(deadlineMs)` (340) bounds time; neither request bytes nor response bytes are enforced (L4-F2, L4-F3). Attempts: per call site via `countModelAttempts` (packages/ledger/src/index.ts:575-589, every outcome counted) and `remainingProviderAttempts` (index.ts:2651-2664); run-wide via `assertModelAttemptAllowed` against `envelope_basis.max_model_attempts` (budget/index.ts:257-265) pinned at ask time (apps/api/src/main.ts:235-241 → packages/register/src/index.ts:172-200, formula `DR-184-v2`): `nodesPerRoot = 2^(depth+1)−1`, `authored = p·nodesPerRoot + p(p−1)` (p>1) else 1, `reviews = authored` (p>1) else 0, `max_model_attempts = (authored+reviews)·(judgeMax+finalRetry) + (maxRecompose·4)·organMax`. With the dev register (JUDGE/COMPOSER/CONFORMANCE maxAttempts 3, tokenCeiling 2048, deadlines 180/60/60 s; `final_retry_attempts` 1; `max_cooldown_holds_per_run` 2; `cooldown_ms` 600 000; `MAX_RECOMPOSE` 2 — apps/runner/src/dev-deployment-register.ts:27-41, dev-runner-process.ts:83-98): p=1 → 28; p=2,d=5 → 1048; **p=3,d=5 → 1584 attempts per ask**; the successful-path call count is 2·authored + ≤8 = 398. `depth` comes from the user's `depth_params` (contract:113; main.ts:238) and is only lower-bounded at ask time (register:175-177); values >5 are refused at claim before any spend (budget:36-46 `depth ≤ 5` → `RUN_ENVELOPE_BASIS_INVALID`, index.ts:1348-1356). Cooldown holds: ≤2 per run × 600 s (index.ts:229-267).
