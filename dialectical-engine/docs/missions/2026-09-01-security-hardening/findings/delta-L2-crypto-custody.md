## Verified-OK controls
- AEAD construction: AES-256-GCM, 96-bit nonce from `randomBytes` per call, 128-bit tag, key and nonce lengths pinned — apps/api/src/support/keys.ts:7-12, 378, 401-408, 448-456, 494-501; per-data-key usage is bounded by `support_limit_session_msgs` (≤100 000, register-publication.ts:550) so random-nonce collision risk is negligible. Wrapped-key AAD binds `{domain=support, kind∈{session,case}, ref}` with length-prefixed fields (keys.ts:129-146) — a session's wrapped key cannot be unwrapped as a case key or for another id (pinned tests/unit/support-keys.test.ts:143-180). v2 content AAD binds `{domain=support-content-v2, kind, session|case, message, role, outcome, purpose}` (keys.ts:184-201), so a ciphertext cannot be moved between messages, roles, purposes (snapshot/summary/message) or sessions/cases; `outcome` and `role` columns are thereby authenticated (support-keys.test.ts:78-93). Envelope versioning: the version byte selects the AAD domain string, so a flipped byte fails authentication; only v1 is a weaker accepted form (DL2-F3). Key commitment: GCM is not key-committing, but every key is 256 random bits from custody or `randomBytes`, never user-derived — no partitioning-oracle surface (INFO).
- Wrap/unwrap: 61-byte fixed envelope `1 || nonce || 32 || tag`, length and version checked before any cipher call (keys.ts:207-223, 424-438); unwrapped length is 32 by construction; `SUPPORT_KEY_DESTROYED` distinguishes the all-zero tombstone from a corrupt envelope (keys.ts:216) and the DB refuses a zero key without `destroyed_at` and vice versa (CHECK `support_session_key_envelope_ck`/`support_case_key_envelope_ck`, 0054:241-248, 311-320), while the deferred integrity trigger requires the matching `shredded_at` and exactly one `shred_audit` row (0054:588-680) — so the zero marker cannot exist outside a complete tombstone set even for the app role.
- Key-domain separation: the support KEK is refused if it aliases KEK/corpus-KEK/blind-index/audit-salt by path string (runtime-environment.ts:274-278), canonical path (realpath), device+inode, or byte content (`timingSafeEqual` on two 32-byte buffers) — keys.ts:310-351, 543-554, wired with all four paths at main.ts:392-400; pinned by support-keys.test.ts:264-315. The support KEK is opened `O_NOFOLLOW` so it cannot itself be a symlink; protected paths are realpath'd then opened `O_NOFOLLOW`.
- Loader parity with the hardened main loaders (L2-F6/B14): `readSupportKek` = `O_NOFOLLOW`, every file decision from `fstat` on the descriptor (no stat→read window), uid, `nlink === 1`, exact 0600, exact 32 bytes, parent exactly 0700 owned by the same uid and refused if a symlink (`lstat`) — keys.ts:244-308; main loader: packages/crypto/src/index.ts:417-462. `FileHandle.readFile()` on a 32-byte regular file allocates an exact `allocUnsafeSlow(32)` buffer (Node `readFileHandle`), so `fill(0)` really erases it. The V-19 rule is identical: exact 0600, same uid, 0700 parent — the support KEK belongs to the API service user; the operator inbox CLI loads it too (support-inbox-cli.ts:196-198) and must therefore run as that uid, while the shred CLI needs only DB credentials.
- Zeroisation on shutdown: `supportKeys.close()` is registered as a pool-shaped entry after `supportPool`/`supportRelayLeasePool` (main.ts:593-596) and `closeDatabasePools` is sequential with per-entry failure isolation (graceful-shutdown.ts:69-82), so the support KEK is zeroed after its pools drain and before the main `kekHandles` are destroyed (:134-148); the forced-close path at the deadline also calls it (:243-249); `startup.run` failures route through the same `close` (startup-resource-owner.ts:34-45). Not the `destroyKek` discipline by name, but the same order. `close()` is idempotent and every later operation fails `SUPPORT_KEY_PORT_CLOSED` (keys.ts:362-364, 530-534; test :237-253). Lease keys are zeroed and quarantined in a `WeakSet` so a closed buffer cannot be reused (keys.ts:366-373, 385-390; test :219-235).
- Shred path semantics (apart from DL2-F1): owner and session shreds take the owner/session advisory locks then `FOR UPDATE` on every session/case/key row (support.ts:1479-1512, 1388-1430), classify LIVE/DESTROYED with coverage checks (1333-1386), zero all wrapped keys and set tombstones in one transaction (1445-1471); message writes, case creation and case-message appends take the same session lock and re-check `destroyed_at`/`shredded_at`/zero key inside the transaction (support.ts:723-743, 835-849, 1196-1209), so nothing is persisted after a shred; unlocked reads see either the pre- or post-commit snapshot in one statement and the API then fails `SUPPORT_KEY_DESTROYED` — a read already past the query cannot be recalled, which is inherent. Session creation for a shredded owner is refused (support.ts:390-397).
- Audit trail (0054): `support.shred_audit` is append-only for the app role (SELECT, INSERT; 0054:855-856, 865, 875), readable by `debateai_support` and the owner only (`REVOKE ALL FROM PUBLIC`); the `_shred_integrity_guard` is inaccessible to the app role (0054:857, 866; attestation support.ts:2403-2409); the guard functions are `SECURITY DEFINER`, `search_path` pinned, body-hash pinned and EXECUTE-revoked from PUBLIC and the app role (0054:507-538, 706-709, 753-787); a deletion or rewrite of an audit row by anyone with UPDATE/DELETE fires the dirty marker and fails the deferred consistency check unless triggers are disabled.
- Error surfaces: every error is a constant code (`SupportKeyError` message = code, keys.ts:90-95; `SupportSessionError` constant strings; DB layer `TypeError(code)`); the CLIs print codes only (support-shred-cli.ts:104-114, support-inbox-cli.ts:213-214); no path or key material in any message. `Math.random` does not occur in the delta files (grep). `timingSafeEqual` is used once, on equal-length 32-byte inputs (keys.ts:548); token comparison is SQL equality on `sha256:` hex (support.ts:443, 458, 507, 685, 1137).
- Register publication: snapshot and request hashes are SHA-256 over 8-byte-length-prefixed `rowKey || valueJsonText || sourceRef` triples sorted by UTF-8 byte order, every `valueJsonText` re-canonicalised before hashing (register-publication.ts:471-482, 494-511, 597-630); the SQL side recomputes both with the same `_lp`/byte ordering and rejects a mismatch (0055:326-333, 628-647, 1489-1506, 1551); decimal and string forms are distinct bytes; objects use `Object.create(null)`, duplicate keys and `toJSON` are refused, depth/size/value counts bounded (:47-49, 221-224, 357-378).
