## 6. R2 — the migration number

dev's `migrations/0061_plan_tier_on_run.sql` is `migrations/0067_plan_tier_on_run.sql`
(`git mv`, content byte-identical); `"0061"` was NOT added to `DUPLICATED_PREFIXES`.

the `ADD CONSTRAINT` that follows it in the same file; `CREATE OR REPLACE FUNCTION
core.create_encrypted_run` — whose only other definition is `0040`, which sorts before
both numbers, so the rename cannot change which definition wins. No statement needed a
change.

re-applies it harmlessly as `0067_plan_tier_on_run.sql`**: the runner (`migrate()` in
`packages/db/src/index.ts`) tracks migrations by full file name, so it sees the new name
as unapplied and runs it once more. Measured on embedded Postgres: after a full migrate,
the old name recorded as such a database has it, and the file applied twice more, there is
exactly one `run_plan_tier_vocabulary` constraint, one `plan_tier` column and a
`create_encrypted_run` that carries `planTier`; both names stay recorded. dev's
compatibility path for pre-plan-tier databases detects the column by schema, never by
file name. Pins moved: `security-migration-0065` (the >= 0065 list names 0067) and dev's
