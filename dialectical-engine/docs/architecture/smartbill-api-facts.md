# SmartBill API — facts the Romanian invoice connector relies on

Checked 29 September 2026. ✅ = stated by a SmartBill page or SmartBill's own sample client; ⚠ = seen only in
third-party integrations or not stated at all — re-check against https://api.smartbill.ro/ in a browser before
changing packages/invoice-smartbill.

| # | Fact | Status | Source |
|---|---|---|---|
| 1 | Base URL `https://ws.smartbill.ro/SBORO/api` (older samples add port 8183) | ✅ | https://ajutorgestiune.smartbill.ro/article/1221-emitere-documente-prin-api ; SmartBill's PHP sample client (`SmartBillCloudRestClient.php`, mirrored at https://github.com/necenzurat/smartbill) |
| 2 | Auth: HTTP Basic, `base64(<account e-mail>:<API token>)`; JSON bodies `Content-Type: application/json; charset=utf-8`, `Accept: application/json` (PDF: `Accept: application/octet-stream`) | ✅ | SmartBill PHP sample client |
| 3 | `POST /invoice` issues an invoice. Fields: `companyVatCode`, `client{name, vatCode, regCom, address, isTaxPayer, city, county⚠, country, email, saveToDb}`, `issueDate` (YYYY-MM-DD), `seriesName`, `isDraft`, `dueDate`, `mentions`, `observations`, `deliveryDate`, `precision`, `currency`, `products[{name, code, isDiscount, measuringUnitName, currency, quantity, price, isTaxIncluded, taxName, taxPercentage, isService, saveToDb}]` | ✅ (county ⚠) | SmartBill PHP sample + https://github.com/necenzurat/smartbill README |
| 4 | Reply: `{errorText, message, number, series, url}`; success = empty `errorText` and a `number`. Some live replies also carry `successfully`/`documentNumber`; an HTML body with HTTP 200 means nothing was created | ⚠ — until ✅, P5 treats a 2xx reply without JSON as `INVOICE_UNKNOWN` (A17b), never as retryable | https://github.com/captainpragmatic/PRAHO/pull/531 |
| 5 | `POST /invoice/reverse` `{companyVatCode, seriesName, number, issueDate}` = storno of the WHOLE invoice, once; a second reversal is refused ("Factura este deja stornata") | ⚠ | PRAHO PR 531; https://glama.ai/mcp/servers/bogdanripa/smartbill-mcp |
| 6 | A PARTIAL correction is a new invoice with NEGATIVE quantities (not a reversal) | ⚠ | smartbill-mcp documentation |
| 7 | `GET /invoice/pdf?cif=&seriesname=&number=` returns the PDF; `GET /invoice/paymentstatus?cif=&seriesname=&number=`; `GET /series?cif=&type=f`; `GET /tax?cif=` lists the account's VAT names/rates | ✅ | SmartBill PHP sample client |
| 8 | There is NO idempotency key and NO lookup of an invoice by our own reference; a replayed POST creates a second, undeletable legal number | ⚠ | PRAHO PR 531 — consequence (A17): an ambiguous outcome is `INVOICE_UNKNOWN`, never retried blindly |
| 9 | Rate limit: 30 calls per 10 s per token (≈3/s); over it, the token is blocked for 10 minutes | ⚠ (spec says 3/s) | PRAHO PR 531; smartbill-mcp |
| 10 | e-Factura: sending to ANAF SPV is an ACCOUNT setting (Configurare → e-Factura → Activează, "imediat după emitere" or 1 h … 4 days); it also applies to invoices issued through the API. No API flag and no API read of the e-Factura status | ✅ setting / ⚠ API scope | https://ajutor.smartbill.ro/article/1153-trimiterea-automata-a-e-facturilor-in-spv ; https://ajutor.smartbill.ro/article/1171-configurare-e-factura ; PRAHO PR 531 |
| 11 | Foreign-currency invoices use the BNR rate by account preference (today's / yesterday's / manual); an API `exchangeRate` field is not confirmed, so we omit it and let the account preference apply | ⚠ | https://ajutorgestiune.smartbill.ro/article/979-facturarea-in-valuta |
| 12 | Standard VAT name for 21 %: `Normala` | ⚠ — read `GET /tax?cif=` once | — |
| 13 | A consumer without a CNP is identified with `vatCode` = 13 zeros for e-Factura | spec §2.5.4 (accountant to confirm) | — |
| 14 | A product sent with `isTaxIncluded: true` and `precision: 2` keeps its `price` as the line's gross total: SmartBill derives the base (price ÷ (1 + rate)) and the VAT (price − base) from it, rounded to the precision | ⚠ — P5 sends the charged gross this way so the invoice equals what the card paid | SmartBill PHP sample (`isTaxIncluded`); rounding not stated |
| 15 | `POST /invoice` with `isDraft: true` saves a DRAFT (ciornă): it takes NO number from the series, is not a fiscal document, is never sent to ANAF's e-Factura system (SPV) even with automatic sending on, and can be deleted in SmartBill; only issuing it later gives it a number | ⚠ — only the field `isDraft` is stated; what a draft does to the series and to e-Factura is not. Until ✅, P5 Step 9 does not offer `--draft` and D7's P23 sandbox run keeps SmartBill off | SmartBill PHP sample (`isDraft` field) |
| 16 | `companyVatCode` (row 3) and `cif=` (row 7) name the company INSIDE the SmartBill account by its CIF, as the account's company details show it; for a VAT payer that may be written with the `RO` prefix or without it — which one SmartBill matches is not stated. Ours is not a setting: it is built from `COMPANY` in `apps/ui/lib/legal/pages.ts` (the facts `/legal` shows, RULINGS-R3 R3-4) through its API mirror `SELLER_COMPANY` (`packages/billing-core/src/company.ts`, P6a) — the bare form is `COMPANY.cui` (digits only, `/legal`'s CUI row), the RO form is `COMPANY.vat.number` (`RO` + the same digits, `/legal`'s VAT row); `COMPANY.cui` is never reshaped for SmartBill | ⚠ — `SMARTBILL_CIF_FORM` (`apps/api/src/billing/connectors.ts`, P6a) is `"bare"` until this row names a form; P5 Step 9's recording sends the digits, so a refusal of its two reads there says SmartBill wants the RO form | SmartBill PHP sample (`companyVatCode`, `cif`) |
