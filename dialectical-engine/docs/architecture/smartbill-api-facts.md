# SmartBill API — facts the Romanian invoice connector relies on

Checked 29 September 2026; re-checked 1 October 2026 against https://api.smartbill.ro/ (SmartBill's own API
reference, "Ultima actualizare: 17 septembrie 2026", read in a real browser together with the OpenAPI document the
page loads). ✅ = stated by a SmartBill page, SmartBill's own sample client or that reference (its section named);
⚠ = seen only in third-party integrations or not stated at all — re-check against https://api.smartbill.ro/ in a
browser before changing packages/invoice-smartbill. Section names below are the reference's own (Romanian).

| # | Fact | Status | Source |
|---|---|---|---|
| 1 | Base URL `https://ws.smartbill.ro/SBORO/api` (older samples add port 8183; the reference names no port). The reference also documents a separate V3 at `https://ws.smartbill.ro/SBORO/api/v3` (Bearer token, CIF in the path) for new resources; invoicing stays on V1 ("Alege V1 pentru facturare si operatiuni curente") | ✅ | https://api.smartbill.ro/ "Introducere → Versiuni API"; https://ajutorgestiune.smartbill.ro/article/1221-emitere-documente-prin-api ; SmartBill's PHP sample client (`SmartBillCloudRestClient.php`, mirrored at https://github.com/necenzurat/smartbill) |
| 2 | Auth: HTTP Basic, `base64(<account e-mail>:<API token>)` (both, and the CIF, shown in SmartBill Cloud → Integrări → API); JSON bodies `Content-Type: application/json; charset=utf-8` (a missing or other Content-Type is `415`), `Accept: application/json` (PDF: `Accept: application/octet-stream`; `*/*`, `application/json` or no Accept also work, `Accept: application/pdf` is refused with `406`). A wrong e-mail or token is `401` with `errorText` "Autentificare esuata…" | ✅ | https://api.smartbill.ro/ "Autentificare V1", "Erori → Erori API V1 → Autentificare", "Facturi → Descarcare factura PDF"; SmartBill PHP sample client |
| 3 | Issuing an invoice is `POST /invoice/v2` ("Emitere factura", `createInvoiceV2`) — **differs from the PHP sample's `POST /invoice`**: the reference documents `/invoice` only as `DELETE` (deleting an invoice), so P5 posts to `/invoice/v2`. Fields: `companyVatCode`, `client{name, vatCode, regCom, address, isTaxPayer, city, county, country, email, saveToDb}`, `issueDate` (YYYY-MM-DD), `seriesName`, `isDraft`, `dueDate`, `mentions`, `observations`, `deliveryDate`, `precision`, `currency`, `products[{name, code, isDiscount, measuringUnitName, currency, quantity, price, isTaxIncluded, taxName, taxPercentage, isService, saveToDb}]` — every one is in the reference's schema, `county` included ("Judetul clientului"). A field name the schema does not know is refused (`400`, `errors[].code` `json_mapping_error`, no `errorText`); a mis-cased one is a `500` with an HTML body. For a buyer in county `Bucuresti` the `city` must be `Sector 1` … `Sector 6`, or e-Factura will not validate in SPV | ✅ (path differs from the sample, see the fact) | https://api.smartbill.ro/ "Quickstart", "Facturi → Emitere factura", "Facturi → Stergere factura", schemas `InvoiceRequest`, `Client`, `Product`; "Erori → Erori API V1" |
| 4 | Reply: `{errorText, message, number, series, url, documentUrl, documentId, documentViewUrl}`; success = empty `errorText` and a `number` (`documentId` is `-1` on an error). The reference says to read `errorText` always, not only the HTTP status. Some live replies also carry `successfully`/`documentNumber`. That an HTML body with HTTP 200 means nothing was created is NOT stated by the reference: it names HTML bodies only for a `500` (a mis-spelled or mis-cased field) and for the PDF's `502` | ⚠ (the HTML-with-200 claim) — P5 treats a 2xx reply without JSON as `INVOICE_UNKNOWN` (A17b), never as retryable | https://api.smartbill.ro/ "Raspunsuri", "Erori → Erori API V1", schema `InvoiceResponseV2`; https://github.com/captainpragmatic/PRAHO/pull/531 |
| 5 | `POST /invoice/reverse` `{companyVatCode, seriesName, number, issueDate}` (`issueDate` optional, never before the original's date) = storno of the WHOLE invoice, once ("O factura poate fi stornata o singura data"); a second reversal is refused (`400`, "Factura este deja stornata.") | ✅ | https://api.smartbill.ro/ "Facturi → Emitere factura storno" |
| 6 | A PARTIAL correction is a new invoice with NEGATIVE quantities (not a reversal). The reference does not describe partial corrections; it does say that `quantity` is not validated ("`0` si valorile negative sunt acceptate, iar documentul se emite fara eroare") and that `price` has a minimum of 0, which fits P5's line (quantity −1, a positive price) | ⚠ — the reference neither confirms nor contradicts it | smartbill-mcp documentation; https://api.smartbill.ro/ schema `Product` (`quantity`, `price`) |
| 7 | `GET /invoice/pdf?cif=&seriesname=&number=` returns the PDF (binary; a missing parameter or a missing invoice is a `502` with an HTML body, not an API error); `GET /invoice/paymentstatus?cif=&seriesname=&number=`; `GET /series?cif=&type=f` (`list[{name, nextNumber, type}]`); `GET /tax?cif=` lists the account's VAT names/rates (`taxes[{name, percentage}]`) | ✅ | https://api.smartbill.ro/ "Facturi → Descarcare factura PDF", "Facturi → Verificare incasare factura", "Configurari → Serii de documente", "Configurari → Cote TVA"; SmartBill PHP sample client |
| 8 | There is NO idempotency key and NO lookup of an invoice by our own reference: the reference's V1 invoice endpoints are only `POST /invoice/v2`, `POST /invoice/reverse`, `GET /invoice/pdf`, `GET /invoice/paymentstatus`, `PUT /invoice/cancel`, `PUT /invoice/restore` and `DELETE /invoice`, each by series and number, and `InvoiceRequest` has no idempotency field; nothing searches `mentions` or `observations`. A replayed POST creates a second legal number. **Differs on "undeletable":** `DELETE /invoice` deletes an invoice for good, but only the LAST invoice of its series; `PUT /invoice/cancel` cancels one (restorable) | ✅ (no lookup, no idempotency key) | https://api.smartbill.ro/ "Facturi" (every V1 invoice section), "Facturi → Stergere factura", "Facturi → Anulare factura"; PRAHO PR 531 — consequence (A17): an ambiguous outcome is `INVOICE_UNKNOWN`, never retried blindly |
| 9 | Rate limit: 30 calls per 10 s per token (≈3/s); over it, the token is blocked for 10 minutes; `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` headers | ✅ | https://api.smartbill.ro/ "Rate limiting V1" (and the page's context note) |
| 10 | e-Factura: sending to ANAF SPV is an ACCOUNT setting (Configurare → e-Factura → Activează, "imediat după emitere" or 1 h … 4 days); it also applies to invoices issued through the API. No API flag and no API read of the e-Factura status: `InvoiceRequest` has no e-Factura field and no V1 or V3 endpoint of the reference reads an e-Factura status | ✅ setting / ✅ API scope (by the reference's full field and endpoint lists) | https://ajutor.smartbill.ro/article/1153-trimiterea-automata-a-e-facturilor-in-spv ; https://ajutor.smartbill.ro/article/1171-configurare-e-factura ; https://api.smartbill.ro/ schema `InvoiceRequest` and its endpoint list |
| 11 | Foreign-currency invoices use the BNR rate by account preference (today's / yesterday's / manual). **Differs:** the reference DOES document an `exchangeRate` on the document ("Daca lipseste, SmartBill foloseste cursul disponibil pentru moneda") and on each product. We still omit it, so SmartBill uses the rate it has for the currency; that this is the account's BNR preference is not stated | ⚠ (the BNR preference) | https://ajutorgestiune.smartbill.ro/article/979-facturarea-in-valuta ; https://api.smartbill.ro/ schema `InvoiceRequest` (`exchangeRate`), `Product` (`exchangeRate`) |
| 12 | Standard VAT name for 21 %: `Normala`. The reference uses `Normala` / 21 in its examples ("Quickstart", "Configurari → Cote TVA": `Normala` 21, `Redusa` 11, `Taxare inversa` 0) but says `taxName` must match the account's own configured names exactly | ⚠ — read `GET /tax?cif=` once (P5 Step 9's `tax-list`) | https://api.smartbill.ro/ "Configurari → Cote TVA", "Quickstart" |
| 13 | A consumer without a CNP is identified with `vatCode` = 13 zeros for e-Factura | spec §2.5.4 (accountant to confirm) | — |
| 14 | A product sent with `isTaxIncluded: true` and `precision: 2` keeps its `price` as the line's gross total: SmartBill derives the base (price ÷ (1 + rate)) and the VAT (price − base) from it, rounded to the precision. The reference says only "Pretul include TVA" (default `false`) and that `precision` takes 2, 3 or 4; how the line is derived and rounded is not stated | ⚠ — P5 sends the charged gross this way so the invoice equals what the card paid | https://api.smartbill.ro/ schema `Product` (`isTaxIncluded`), `InvoiceRequest` (`precision`); SmartBill PHP sample (`isTaxIncluded`) |
| 15 | `POST /invoice/v2` with `isDraft: true` saves a DRAFT (ciornă): it takes NO number from the series, is not a fiscal document, is never sent to ANAF's e-Factura system (SPV) even with automatic sending on, and can be deleted in SmartBill; only issuing it later gives it a number. The reference states the number half in words ("fara numar atribuit … pana la finalizare manuala din SmartBill Cloud"); it says nothing about e-Factura, the fiscal status or deleting a draft | ⚠ — the e-Factura half is not stated. Until ✅, P5 Step 9 does not offer `--draft` and D7's P23 sandbox run keeps SmartBill off | https://api.smartbill.ro/ "Facturi → Emitere factura" (example 5, "Emitere factura ciorna (draft)"), schema `InvoiceRequest` (`isDraft`); SmartBill PHP sample (`isDraft` field) |
| 16 | `companyVatCode` (row 3) and `cif=` (row 7) name the company INSIDE the SmartBill account by its CIF, "exact ca in SmartBill Cloud" / "CIF-ul exact al firmei active din contul Cloud"; the Quickstart says to copy it from SmartBill Cloud → Integrări → API. For a VAT payer that may be written with the `RO` prefix or without it — which one SmartBill matches is not stated (a CIF it does not match is a `401`, "Firma la care incercati sa va conectati nu mai este disponibila in Cloud."). So the form is whatever the Integrări → API page shows. Ours is not a setting: it is built from `COMPANY` in `apps/ui/lib/legal/pages.ts` (the facts `/legal` shows, RULINGS-R3 R3-4) through its API mirror `SELLER_COMPANY` (`packages/billing-core/src/company.ts`, P6a) — the bare form is `COMPANY.cui` (digits only, `/legal`'s CUI row), the RO form is `COMPANY.vat.number` (`RO` + the same digits, `/legal`'s VAT row); `COMPANY.cui` is never reshaped for SmartBill | ⚠ — `SMARTBILL_CIF_FORM` (`apps/api/src/billing/connectors.ts`, P6a) is `"bare"` until this row names a form; P5 Step 9's recording sends the digits, so a refusal of its two reads there says SmartBill wants the RO form | https://api.smartbill.ro/ "Quickstart" (Pasul 2), "Erori → Erori API V1 → Autentificare", schema `InvoiceRequest` (`companyVatCode`); SmartBill PHP sample (`companyVatCode`, `cif`) |
