# Self-report — REV-S01-p1-security-data-safety

> treat it like a murder case. I want to get a nice report on what can be done better. What we must upgrade. what repeatedly costed us tokens. how we can make the coding more efficient. How can we turn this into a one prompt machine even better.

Seat: REV(S01) blind lens security/data-safety, pass 1, ticket `t_af8d9bb2`. Verdict PASS with N1…N7. Wall clock ~35 min, one session, no rework.

## The cause, not the symptom

**The case turned on one query, and I nearly wrote 4,000 words of trigger exegesis before running it.** The slice's whole security story is two pinned admissions in a `BEFORE INSERT` trigger keyed on fixed UUID tokens. Reading them, the natural review is a close reading: which predicates, which order, what can be forged. I spent the first third of the run doing exactly that. The question that actually settles it is four lines of SQL — `has_table_privilege(role, 'core.run_visibility_event', 'insert')` for every `debateai%` role. The answer is that **nobody but the schema owner can insert at all**, which collapses the entire forgery surface to zero and reduces every trigger weakness I then found (N1, N2, N3) from "blocking" to "defence in depth". Ten minutes of privilege enumeration, done first, would have reframed the whole review.

The generalisable rule: **on a database-authorization slice, enumerate the privilege grid before reading a single predicate.** Predicates only matter to roles that can reach the table. This belongs in the reviewer contract as a named first step for any slice whose diff contains a migration, and it is the single largest token saving I can name here — it would have cut my trigger-reading pass roughly in half.

## What repeatedly cost tokens

1. **Fixture re-derivation — the biggest line item, ~4 probe iterations.** I wrote three probe files that each needed a realistic account + session + run + attestation-secret fixture. That fixture is ~70 lines of schema-specific SQL with a content-envelope HMAC in the middle. I got it wrong three times in a row on details that have nothing to do with security: a duplicated `session.token_hash` (the C2 test deletes the session after seeding; I did not), a `$1::text` that collided with `$1::uuid` in the same statement, a fake `content_ciphertext` that failed `publication_snapshot_check`, and a `MemoryPublicationKeyStore` that refuses a second `create()` for the same ref. Four full embedded-Postgres boots at ~8 s each plus four read-fix-rerun cycles. **Upgrade: `tests/support/` needs a `seedOwnedRun()` helper.** Every one of C1, C2, C4 and both of my probes hand-rolls the same fixture. It is the most-copied 70 lines in the slice, and copying it is how each copy drifts.
2. **`pg_get_functiondef` mutants were cheap; file mutants would have been expensive.** Replacing the function body in the ephemeral probe database, running the case, then restoring from the captured text, cost ~30 s for three mutants and left the worktree byte-clean by construction. Doing the same by editing `0067` and re-migrating would have cost a boot per mutant and risked the restore-law trap the board already has a ticket for (`t_d3cd954d`). **Upgrade: make in-database `CREATE OR REPLACE` mutation the documented default for any SQL guard**, and say so in the packet's charge-4 wording, which currently says "remove each guard in a mutant" without saying where the mutant lives.
3. **One dead end worth naming so nobody re-derives it.** I tried to characterise the f1 admission by inserting a visibility row as the schema owner. It fails with `23503` — `run_visibility_event_publication_ref_fkey` — because the row references `serve.publication_snapshot`, which must exist first. The f1 admission therefore has a structural gate the trigger text does not show. I wasted a cycle concluding "the trigger admits an unbound run" when what I had measured was a foreign key. The f2 probe worked because the snapshot already existed from a real publish. **If you probe a trigger admission, publish for real first, then mutate the row you insert.**
4. **Contaminating my own input.** For R-6 I planted the owner's email, user id and session id inside the answer's question line and summary text, then reported a leak. The publish path had faithfully copied user-authored text — exactly as the owner-driven path does. The correct probe uses a clean answer, so anything found is something the *machinery* added. I caught it before writing the verdict, and it turned into N7 (the SPEC's R-6 check has the same flaw). Cost: one probe re-run. **This is the failure mode of "exceed the author's parameters": exceeding them is only evidence if the excess is on the machinery, not on the payload.**

## What I nearly got wrong

Reading the diff hunk for the unpublish route, the 409 appears immediately after the ownership 404, with no grant check in sight — it looks exactly like an R-13 violation and I started drafting it as a blocking finding. The hunk's context simply began below `preflightGrant`, which is 22 lines earlier at `index.ts:1175`. **A diff hunk is not a control-flow ordering.** I only caught it because I opened the file at the head before writing the finding. For an ordering claim, read the function; the hunk cannot show you what precedes it.

## Where this packet was unclear, exactly

- **The `inputs` line is exhaustive and omits the one source the role contract requires.** `heartbeat-reviewer` §1 makes checking each author's `SKILLS LOADED` line mandatory; the packet's "read these and nothing else" names no artefact that carries one, and the agent-reports in the package carry none. This is N6 and it forced an UNVERIFIED that no reading inside my contract could remove. Fix: quote each author's `SKILLS LOADED` line into review-package §3.
- **Charge 4 says "remove each guard in a mutant" and never says where the mutant lives** — file, migration, or live database. Three readings, three very different costs. See upgrade 2.
- **The verification line demands "every cluster command re-run by you" but the three-run rule is not restated**, so it is ambiguous whether a lens owes one run or three. I ran twice and declared the three-run table UNVERIFIED. Fix: say `one run per lens; the three-run table is the correctness lens's` in the packet, or say three.
- Charge 2 asks whether `0068` preserves every branch of `0067`'s trigger, which is a 12-line diff. It does not ask the larger question in the same migration: `0068` also redefines `core.prepare_private_run_erasure`, a 180-line SECURITY DEFINER authorization function. I diffed it against `0040` anyway (it preserves everything and adds a guard), but a packet that names the small redefinition and not the large one is steering the lens away from the bigger surface.

## Upgrades, ranked by tokens saved

1. **Privilege grid before predicates**, for any slice whose diff contains a migration. Reframes the review, and turns most trigger findings into correctly-tiered N-findings instead of contested B-findings that cost a rework round.
2. **`tests/support/seedOwnedRun()`.** Kills the most-copied 70 lines in the mission and the four fixture retries every seat pays independently.
3. **In-database `CREATE OR REPLACE` as the documented mutant mechanism for SQL guards**, with capture-and-restore asserted byte-identical in the probe itself.
4. **Packets carry the authors' `SKILLS LOADED` lines**, so the mandatory check is inside the contract instead of outside it.
5. **Pin `--encoding=UTF8` wherever a test builds its own Postgres** (N5). Not a token saving for me — an evidence saving for everyone downstream, because a `0/0` BROKEN suite reads as noise and gets re-run before it gets diagnosed.

## Toward one prompt

The part of this run that needed judgement was choosing *which* six attacks to build. The part that did not was everything around it: the fixture, the role-switching helper, the mutant capture-restore, the probe promotion script, the byte-clean check. That scaffolding is identical for every database-security lens this fleet will ever run, and I rebuilt it from scratch. A `heartbeat-reviewer` sub-skill carrying exactly those five pieces — privilege-grid query, seeded owner fixture, `withRole`, `withMutant`, and a promotion runner that takes `$WORKTREE` — would let the next security lens spend its whole budget on the attacks and none on the harness. That is the concrete shape of "one prompt": not a longer packet, but a shorter one pointing at a harness that already exists.
