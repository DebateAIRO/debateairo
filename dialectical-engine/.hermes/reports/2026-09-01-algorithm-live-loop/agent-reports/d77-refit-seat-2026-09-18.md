## O2 — what an operator with tonight's `acceptance/.pgdata` gets on the next run, and why

**They get a loud stop at seeding, before any model call: neither the new pair
nor a silent run on the old one.** The ceremony reads every T16 family at
`ACCEPTANCE_REGISTER_VERSION` (`acceptance/seed-register.ts:24`, pinned at `2`;
read at `acceptance/runtime-policy.ts:291-295` and passed whole to the runner at
`acceptance/main.ts:503,598`), and the rows get into that version through
`seedAcceptanceRegister` (`acceptance/seed-register.ts:393-407`), which calls
`importHistorical` — **not** `publishGeneral`. `importHistorical` is replay-only:
`register.import_historical_register_version`
(`migrations/0055_register_support_publication.sql:1343-1374`) finds that version
2 already exists, compares `register._snapshot_sha256(2)` against the digest of
the rows it was handed, and on any difference raises
`REGISTER_PUBLICATION_SEAL_INVALID: historical replay drift`; only a byte-identical
snapshot returns `REPLAYED`. So **sealed means immutable per version**: the seed
neither overwrites nor merges nor inserts-if-absent, and a standing `.pgdata`
keeps δ 0.02 / ε 0.01 for exactly as long as it stands — but it also cannot be
used for another ceremony while the code carries the refit, because the seeding
step that precedes the run now refuses. This is the same discipline
`acceptance/README.md:44-46` and `:162-165` already document for earlier row
changes ("reset the standing data directory rather than mutating sealed rows").
Measured, not argued, at
`tests/integration/t16-algorithm-register.test.ts:536-558`: an acceptance v2
sealed with the pre-refit pair makes `seedAcceptanceRegister` reject with
`/historical replay drift/`, leaves the sealed snapshot byte-identical, and still
reads back `{ delta: 0.02, epsilon: 0.01 }`. **The two ways forward are therefore
(a) the operator resets the standing acceptance data directory, which loses
tonight's run database, or (b) the pinned version is raised to 3 at
`acceptance/seed-register.ts:24`, which mints a new sealed version beside the old
one and leaves run `d7b73d79` intact — I verified a bump needs no migration and
no other edit** (the `BEFORE INSERT` trigger
`register._algorithm_publication_profile_guard`,
`migrations/0061_algorithm_publication_profiles.sql:10-37`, auto-declares the new
version's `required_row_version` profile and asserts the mandatory rows;
`importHistorical` caps at version 4 —
`packages/register/src/register-publication.ts:777` and
`migrations/0055_register_support_publication.sql:1288` — so that ladder has two
rungs left) **— but (b) is the BLOCKED line above and I did not make it.**

**The development deployment behaves differently, by design, and needs nothing.**
`seedDevelopmentDeploymentRegister` (`apps/runner/src/dev-deployment-register.ts:726-779`)
derives its publication id from the snapshot hash of the rows
(`:762-766`), so the refit is a *different* publication:
`register.publish_register_version` does not find it
(`migrations/0055_register_support_publication.sql:1506-1531`),
`register.allocate_register_version()` mints the next unused version
(`:1219-1249`, sequence-based, floor > 4), and the runtime pins that version from
