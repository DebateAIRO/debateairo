## Findings and concerns

**F1 — THE ONE DECISION I LEFT OPEN. Moving the bootstrap pin moves a hash a production runbook
depends on.** `tests/support/registerFixtures.ts:17-18` holds
`LEGACY_REGISTER_V1_SNAPSHOT_SHA256 = "8fde270c…"`, asserted as a literal at
`tests/architecture/register-support-publication.test.ts:356` and recomputed from today's
`register.bootstrap.json` at `:382` and at `tests/integration/register-support-publication.test.ts:362`.
Because the snapshot hash covers each row's `sourceRef` as well as its value
(`packages/register/src/register-publication.ts:603`), changing `nodeRuntimeVersion` moved it to
`db282408…`. Re-pinning the constant is a two-line change and would clear both NEW rows — I did not make
it, for two reasons. First, it is outside this task's allowed writes. Second, and the reason I did not
ask for a widening: that constant is not only a test fixture.
`docs/missions/2026-08-17-accounts-privacy-security/P3-02-production-database-principal-provisioning.md:163-165`
instructs the operator, as step 2 of the production order, to confirm that exact v1 snapshot SHA-256 in
the deployed database. A repository that has quietly re-pinned it would disagree with deployed history,
and `persistBootstrapRegister` (`packages/register/src/index.ts:669-693`) would throw
`FX-REG-SEALED_VERSION_MISMATCH` against any database that already has v1 sealed — including a developer
database previously seeded by `pnpm dev:auth:seed-register`
(`apps/runner/src/dev-deployment-register.ts:717`). The two candidate resolutions, for the orchestrator:
re-pin the constant and amend the runbook line in the same commit (correct if no V3 database has ever
sealed v1), or give v1 a frozen row fixture of its own the way v4 already has one
(`tests/support/registerFixtures.ts:102-106`) so the bootstrap file can keep evolving. Both are larger
than this task. **Nothing is silently broken either way: the two rows are red and named.**

### The full runs at `53a09658`, and a correction to my own classification

The orchestrator ran the full suite twice at `53a09658` after my fix round. I read both result sets

my own 48-row list:

| in my 48, gone at `53a09658` (loaded) | the two v1-hash rows — the revert, as predicted — **and** `S3b keeps live-mail N=1/N=4/N=8 PostgreSQL arms below the separation ceiling` |

| loaded, gone when quiet | that same `keeps new-vs-existing timing …` row, and nothing else |

So 48 − 3 + 1 = 46, and 46 − 1 = 45. The arithmetic landed on my number by a different route than I
drew it: one of my two (d) rows did not recur, and a third row of the same family took its place.

**The correction I owe.** My O4 section classified both `S3b keeps live-mail …` and
`S3d rework3 B1/B3 …` as (d) environment on the evidence of an isolated 3/3 pass. That evidence was
sufficient for one row and not for the other:

- `S3b keeps live-mail …` and `keeps new-vs-existing timing …` are **(d) environment, now confirmed by
  a control I did not have**: the second appears under load and vanishes on a quiet host, and the
  mechanism is visible in its own numbers — loaded `new_ms=1329.9 duplicate_ms=712.8 delta_ms=617.1`,
  quiet `delta_ms=14.7 / 15.2 / 4.0` with `new_ms=718.7 / 711.0 / 704.3`, inside the pre-upgrade 716-728
  range. Only the real-work arm moved and the floor-pinned duplicate arm did not, which is what CPU
  contention does to an argon2id hash.
- `S3d rework3 B1/B3 …` is **red on the quiet host too, so my (d) label was wrong** — it is not host
  noise. It is still not upgrade-caused, so the "not (a), not (b)" half of my classification stands, but
  the cause is statistical rather than environmental, and on the quiet host it fails at a DIFFERENT
  assertion than in my run: `:2991` `expect(assertion.auc).toBeLessThanOrEqual(assertion.aucCeiling)`
  with `0.78515625` against `0.76953125`, where my run had already failed at `:2988` and never reached
  it. Checked at the source: the ceiling is not a constant but
  `empiricalQuantile([...existingNull.auc, ...missingNull.auc], 0.99)`
  (`tests/integration/registration-database.test.ts:2835`), a null built by relabeling same-arm samples
  — so the assertion is a permutation test that rejects about 1 % of the time with no signal present,
  and the run makes a dozen such comparisons. The baseline corroborates the thin margin:
  `auc=0.7266 null_auc_q99=0.7617` passed there. Ticketed by the orchestrator as
  `F-S3D-SEPARATION-PERMUTATION-FLAKE`; nothing for me.

The honest lesson for the record: "passes 3/3 in isolation" separates a deterministic regression from
everything else, but it cannot tell load apart from a false-positive rate. UNVERIFIED U3 said exactly
that, and the quiet control is what resolved it.
