## r1

# T3 codex review case file

## Cause and price

The principal rework cause is temporal, not surprising: the worker filed before J12
existed. Its own F6 deliberately chose a receipt-level
`PANEL_WEIGHTING_UNCONFIGURED` fallback to avoid disturbing eight M>=2 database
fixtures; J12 later ruled the opposite policy and explicitly made those fixtures and
their paired failure payloads T3 coherence work. Price: one expected review/rework
round, one runner guard replacement, eight fixture provisions, and paired base/HEAD
evidence for a file already in the stable-red set. Treating this as a novel worker miss
would make the fleet's history dishonest.

The acceptance gap has a different cause: the acceptance seeder currently derives one
family from each maker, so every configured provider is the first member of its family.
The receipt proves that family resolution and the discount stage ran, but it cannot
execute the multiplier branch. Price: r1 spent mutant effort proving UNKNOWN-family
resolution while the higher-value ordinal-2 path remained unreachable. The schema
already permits multiple provider refs in one family, so the repair is fixture-sized,
not architectural.

The partial-panel gap is a topology mismatch. An M=2 fixture can express healthy or
all-other-failed, never "one other failed and one other survived". The M=3 unit probe
stops at `runJudgePanel`; it never reaches the runner branch that writes
`PANEL-PARTIAL`. Price: a production branch and named mark reached review with no
discriminating receipt assertion.

## What repeatedly cost tokens

- The dispatch packet repeated two already-known packet defect classes. It said
  "visible mark" without naming the partial vocabulary member or writable visibility
  surface (the F9 class), forcing the worker to choose policy. It also called paths
  absolute while abbreviating the mandatory self-report and logs with `...` (the F12
  class), forcing board reconstruction.
- The worker had to reason around eight database fixtures without a shared panel-policy
  fixture helper. J12 now makes the missing helper unavoidable; centralizing it will be
  cheaper than editing eight object literals instance by instance.
- The acceptance provider doubles still include a dead quoted-fragment classifier that
  falls back to FIFO. That converts fixture drift into misleading production failures
  and caused the worker's first RED to fail for the wrong reason.
- Load-sensitive tests were re-litigated again. One is a new obs-capture signal-kill
  instance; the registration RSS flip belongs with F22. Both need named tracking so
  later lanes do not spend another classification pass.

## What I nearly got wrong

I nearly accepted "family ordinal present" as proof that the repeated-family discount
was live. It proves the stage and sealed-map resolution, but with every ordinal equal to
1 it does not prove the ruled multiplier can affect a receipt or selection. The review
packet's explicit same-family question prevented that false approval.

I also nearly collapsed J12 into one loud-stop finding. Its ruling has three separately
auditable obligations: stop behavior, eight coherence fixtures with unchanged
assertions, and paired base/HEAD failure payloads. Keeping them separate makes r2
completion mechanically checkable.

## Dead ends and ruled-out suspicions

- I did not run tests or builds: this seat's packet forbids them. Existing logs were read
  as upstream evidence; all fresh probes were static.
- Duplicate values in `panelContractHashes` are not by themselves a finding: the field
  records the contract hash for each surviving voice, and every member currently uses
  the same judge contract.
- The walking-skeleton literal has one production call site behind
  `effectiveMakerCount <= 1`; both root and child producers call the shared panel helper.
  Static tracing found no third judgement producer.
- F29 and F30 are already routed. Re-filing them would duplicate state rather than fix
  it: F29 owns the hand-declared orphan list, and F30 owns serve-side consumption of the
  recorded band step-down.

## Packet clarity and one-prompt upgrades

The r1 reviewer packet was unusually effective where it mattered: it framed J12 as
expected rework and asked the exact same-family question that distinguished stage
execution from arithmetic execution. The original worker packet fought the seat at
`t03-panel.md:8-10` (non-resolving path abbreviations) and `:32-35` (unnamed/unsurfaced
partial mark).

For the next one-prompt machine iteration:

1. Inject rulings created after worker filing as an explicit, itemized expected-rework
   checklist, as this reviewer packet did for J12.
2. Packet-lint every mandatory path with an existence/resolution check; reject `...` in
   writable or deliverable fields.
3. For every conditional acceptance property, require a fixture whose topology reaches
   the non-identity branch. "Stage called" is not enough for a multiplier, downgrade,
   retry, or fallback.
4. Generate fixture blast-radius rows from static construction sites. Here that would
   have emitted the exact eight `scoringOperator`-bearing M>=2 fixtures before coding.
5. Combine r2's M=3 fixture work: a seeded same-family pair can exercise ordinal 2 while
   a third provider failure exercises `PANEL-PARTIAL`, paying one standing-database boot
   for two independent properties.

# T3 codex rework-verification case file

## Cause and price

The remaining miss is temporal ruling content, not a surprise. The worker froze its r2
report while N1 still said that the partial-mark vocabulary and surface awaited
ratification. J13 arrived afterward and did two separate things: it closed the
receipt-as-surface question, and it required `PANEL-PARTIAL` to be minted through the
canonical `CONDITION_MARKS` path under T4's mid-list/schema/projection discipline. The
r2 code implements the receipt string but predates the second obligation.

Price: one focused final rework round. It must add the canonical vocabulary member,
prove the contract schema accepts it, project it through the condition-mark path, and
retain the already-good raw receipt proof. Because the repair necessarily touches the
kernel vocabulary, it also changes the worker's current “D16 does not gate” scope fact;
the final handoff must account for the resulting gate rather than copying the r2 claim.

## What repeatedly cost tokens

- A post-worker ruling was dispatched directly to review while the worker artifact still
  truthfully described the question as open. The packet made the new obligation clear,
  but the lifecycle guarantees another round because no implementation continuation sat
  between ratification and verification.
- “Canonical mark” is a cross-layer term. A repository-local constant and JSONB receipt
  look convincing until the kernel vocabulary, imported Zod enum, serve record union,
  and answer/node projection are checked together.
- The B4 mutant log trips the earlier `effectiveWeight` assertion before reaching the
  final `row.tau` assertion. Static inspection still verifies that the outcome is pinned,
  but the log by itself does not demonstrate that final assertion.

## What I nearly got wrong

I nearly read J13(c), receipt-as-surface, as superseding J13(b)'s projection requirement.
They are separate clauses: the existing ledger receipt is the lawful acceptance proof
surface, while the named value must also belong to the canonical condition-mark
vocabulary and projection machinery. The packet's explicit “mid-list, schema,
projection” checklist prevented a false approval.

I also paused on the B4 mutant output because it fails at the intermediate weight. The
shipped test nevertheless has a distinct final-outcome pin: with B's 0.9 discounted to
0.45, A's 0.5 remains selected, and `row.tau` is asserted as 0.5. That closes the finding
statically even though a reordered mutant assertion would make the evidence cleaner.

## Dead ends and ruled-out suspicions

- I ran no tests, builds, provider calls, or product writes. Existing RED/GREEN and paired
  database logs were inspected only as upstream evidence, as the packet requires.
- B1's guard is before claim and spend; its test pins typed code, READY/unclaimed state,
  and zero calls on both doubles. The mono sibling excludes the loud-stop code.
- The 24/24 count is coherent: each provider keeps 16 original author/review calls and
  gains eight panel assessments of the other provider's eight authored nodes.
- The B3 payload remains the same one-test `staleness_state` failure; the only structural
  changes are three added tests and a +297-line shift, yielding 60/61 to 63/64.
- N4's original ceremony defect is closed: its escape-safe classifier no longer serves a
  wrong-class FIFO head. The integration helper fixes the dead classifier too; its more
  permissive FIFO behavior is outside the original ceremony finding.

## Packet clarity and one-prompt upgrades

The r2 packet was precise and did not fight the review. Its J13(b) wording named the exact
cross-layer mechanics that exposed the miss; without that checklist, the receipt test
would likely have been mistaken for complete canonical minting.

For the next one-prompt machine iteration:

1. When a ruling lands after a worker marker, dispatch one worker continuation before the
   reviewer, or label each post-marker item explicitly as expected next-round content.
2. Expand “mint a canonical mark” mechanically into: mid-list kernel member, contract
   parse proof, record/type admission, answer and affected-node projection, and a real
   projection assertion.
3. Recompute evidence gates from the required fix surface. A ruling that mandates a
   kernel/contract vocabulary edit should automatically invalidate an earlier “D16 does
   not gate” statement.
4. Put decisive outcome assertions before diagnostic intermediate assertions in mutant
   fixtures when the report intends the mutant log itself to prove the outcome.

## Cause and price

The product implementation now carries both panel-degradation marks through the same
canonical path, but the proof does not carry both arms through the same path. The worker
correctly added `PANEL-DEGRADED-SINGLE-VOICE` as J5 forced completion beside
`PANEL-PARTIAL`; however, its existing all-failed acceptance test was inherited unchanged
from r1 and still reads only `ledger.reduced_judgement.disagreement.marks`. The new M=3
partial test alone calls `ServeRepository.readAnswerProjection` and inspects a node-scope
typed record. The final packet explicitly asked for five-step equality on both arms, so
source symmetry cannot substitute for the missing sibling production-seam assertion.

Price: there is no authorized round 4. The residue must be V-packet-row-ready. The code
repair appears fixture-sized and test-only: extend the existing all-failed acceptance arm
to resolve its answer, read the canonical projection, and pin both the answer mark and
the affected-node record. A second record residue is cheaper still: the report quotes a
TS2367 RED frame, but no filed T3 log contains it.

## What repeatedly cost tokens

- The raw-receipt/canonical-projection distinction recurred one branch over. The partial
  arm was upgraded from raw JSON to `readAnswerProjection`; the all-failed arm retained
  the old raw assertion and therefore looks stronger than it is.
- A shared union and shared projection loop make implementation symmetry easy to verify,
  but also make it tempting to infer branch-proof symmetry. A one-arm filter regression
  is exactly the mutation that separates those claims.
- RED prose and RED capture diverged. Vocabulary and projection RED logs exist and contain
  the desired failures; TS2367 exists only as a quotation in the worker report.

## What I nearly got wrong

I nearly approved the sibling because `PanelDegradationMark` includes both values and the
runner maps every `panelDegradations` record into a typed `ConditionMarkRecord`. That is
good current code, but it does not satisfy the packet's branch-specific fifth step. If a
later edit filters the projection to `PANEL-PARTIAL`, the vocabulary/schema test, the M=3
projection test, and the all-failed raw-receipt test all remain green.

The acceptance test's name also nearly fooled me: “marks
PANEL-DEGRADED-SINGLE-VOICE” sounds canonical, and the fixture does run the real runner.
Its assertions nevertheless stop at a direct SQL read of the untyped disagreement JSON;
it never exercises `ConditionMarkSchema.parse` on the produced sibling mark.

## Dead ends and ruled-out suspicions

- B6's five-step path for `PANEL-PARTIAL` is complete: safe mid-list kernel member,
  contract parse proof, serve union, typed node projection from both judgement producers,
  and real `readAnswerProjection` consumption.
- The sibling's current production mechanics are equal on steps one through four. The
  finding is the absent step-five discriminating proof, not a claim that current product
  code drops the mark.
- The three 29-to-31 count pins remain exact, the two exhaustive presentation switches
  add exactly one branch per new member, and generated contract output remains unchanged.
- D16's apps/ui and web base/HEAD logs are byte-identical one-line TS2882 failures. They

  filed. The 11-file r3 delta is confined to B6 and its forced completions.
- I ran no tests, builds, provider calls, or product writes; the final packet forbids
  them. Existing logs are upstream evidence only.

## Packet clarity and one-prompt upgrades

matrix was more precise than the worker report's narrative claim that a shared projection
made the sibling complete.
