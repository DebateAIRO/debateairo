## What happened

The GUIDE_LIVE failure revealed that the final exact-product row proof existed only inside the browser capture entry point. GUIDE_ROW_PROOF prepared a separate adapter around the same sealed constructor. It cannot continue into Playwright or Support traffic. It binds the matrix, verifier, harness digest, revision, inventory, attestation, suite, control proof, and capacity receipt, then exposes fixed per-row metadata only after all 54 proofs genuinely derive.

Nothing was run. The result is `PREPARED_NOT_EXECUTED`, not an all-54 PASS.

## What repeatedly cost tokens

- The original inert controls used dependency stubs, while the final product-bound proof lived inside capture. That split allowed a real shared-article action mismatch to survive until after lifecycle and capacity work.
- The product-bound constructor combines deterministic row proof with operational capacity freshness. Reusing it honestly means the proof-only adapter still needs a fresh capacity-bound gate to return success.
- The sealed constructor short-circuits on the first row failure and exposes `prepare(row)` only after every proof derives. Per-row continuation on failure cannot be added without changing the verifier interface or copying proof logic.

## Upgrades

1. Keep the exact-product proof adapter as a first-class reviewed preflight in the future one-prompt sequence.
2. In a later versioned harness, separate immutable product/corpus proof construction from runtime capacity validation while preserving a final combined gate before traffic. This would let composition catch row mismatches before starting or stopping services.
3. Export a versioned sequential proof iterator from the harness so fixed row attribution is available on first failure without duplicating logic.
4. Generate the final run order from one gate-aware orchestrator: compose evidence, start supported preview, measure capacity once, run all-row proof, then capture only on pass.
