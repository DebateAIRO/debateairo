## Murder-case retrospective

The repeated cost was rarely the final code. It was uncertainty carried between nodes. The mission repeatedly had to rediscover which bytes were authoritative, which review bound which digest, whether a runtime represented current HEAD, and which passing frame still covered the latest edit. Every correction then needed a new packet, lease handoff, partial rerun, manifest, receipt, review, and preview. Those controls protected the security boundary, but manual bookkeeping multiplied token use and made a small product behavior change span many sessions.

Four patterns caused most of the rework:

1. **Examples stood in for classes.** Credential, internal-identifier, delimiter, negation, and product-name failures were initially patched around witnessed strings. Generated class matrices and paired benign controls found the remaining variants later. The first implementation should derive grammar/class properties from the policy and generate boundary cases before code.
2. **Knowledge bytes and admission bytes moved separately.** Articles, projections, fallbacks, catalog canonicalization, component files, and editorial manifests form one logical artifact but were authored and hashed by separate manual steps. A corpus compiler should emit candidates, validate bilingual completeness, compute every digest, prepare a reviewer packet, and produce the manifest patch only from the reviewer result.
3. **Verification ownership was fragmented.** Heavy leases, embedded databases, preview lifecycle, inherited typecheck diagnostics, and exact test unions were coordinated by prose. A machine-readable test plan should map each changed path to its required suite, record the revision and command, invalidate only superseded frames, and schedule the heavy lane once.
4. **The live relay was used too early as a diagnostic surface.** Non-deterministic model output exposed real defects, but it also blurred prompt quality, native schema support, model behavior, and deterministic policy. A deterministic relay fixture should establish source/action contracts and security predicates first; one bounded real-relay smoke should confirm the assembled system afterward.

The path to a stronger one-prompt machine is to compile one owner prompt into an executable mission contract rather than a chain of prose packets. That contract should contain: acceptance examples and counterexamples; immutable base/source/runtime revisions; path ownership; dependency graph; policy invariants; corpus and editorial stages; generated test classes; required commands; lease needs; and exact receipt schemas. The orchestrator can then dispatch only independent nodes, automatically reject stale evidence, and stop creating new planning turns for facts already encoded in the graph.
