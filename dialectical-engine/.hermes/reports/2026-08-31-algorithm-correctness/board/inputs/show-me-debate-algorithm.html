DebateAI algorithm · current working tree

What happens between a question and a verdict?

Every important data transformation, model call, formula, gate, persistence decision, current limitation, and improvement seam—in actual execution order.

Two truths to keep separate

Algorithm body

The fully wired acceptance runtime can execute the pipeline below.

Production entry point

apps/runner/src/main.ts omits required judgement policy, serve policy, terminal evaluator, multi-maker gateways, and scoring configuration. As written, it stops before the first model call.

PHASE 01

Intake: raw question → durable run

1

Browser builds an AskRequest

The question is bundled with risk tier, composition-budget tier, depth, personal decision scope, machine timestamp, steering presets, and free-text steering annotations.

{ question_line, risk_tier, tier_source: "ASKER",
  composition_budget_tier, depth_params: { depth },
  decision_scope: "personal", as_of,
  steering_presets, steering_annotations }
InputForm fields
TransformStrings + depth conversion
OutputTyped AskRequest
UI accepts every positive integer depth; the runner later accepts only 1–5.
2

API validates the exact object

Zod trims the question, rejects empty values and invalid vocabularies, validates ISO time, and rejects extra keys. The question is not summarized or semantically rewritten.

InputRaw JSON body
TransformStrict schema parse
OutputTrimmed validated ask
3

Admission resolves risk, panel, and structural ceiling

  • Resolve effective risk and provenance; deployment policy can override asker selection.
  • Read recent healthy provider probes and freeze maker/model identities.
  • Require maker availability appropriate to effective risk.
  • Compute maximum work implied by panel size, depth, branching, retries, composition, and conformance.
A question can be refused here before any debate model sees it.
4

Run contract is frozen and encrypted

A UUID run stores question, identity scope, as-of time, risk decision, panel, depth, composition tier, register/battery versions, cost-envelope basis, steering data, and initial battery activation rows. Authenticated-run content is encrypted at rest.

Steering data is stored in askContract, but readFrozenHead() does not return it. The runner never places it in model prompts.
5

Durable Q1 work is queued

The API records liveness/memory information, inserts a READY work item with idempotent command key S00:<runId>:Q1, dispatches Hatchet, and returns HTTP 202. The UI navigates before an answer exists.

READY → CLAIMED → SETTLED | FAILED
PHASE 02

Root judgement: question → statement + τ

6

Runner preflight and idempotent claim

Before claiming work, the runner requires coherent deadline/lease values, claim-type composition, judgement selection, serve policy, and—when multiple makers create arrows—a scoring operator. It checks the ledger for an already successful command or exhausted attempt.

The production entry currently fails at this boundary. Acceptance supplies the missing settings.
7

Frozen panel is checked again

Ask-time identities are compared with gateways configured in this process and optional claim-time probes. Missing gateways, absent models, or changed model IDs are removed.

effectiveMakerCount = healthy pinned makers with configured gateways
1 maker  → root only; requested depth is not expanded
2+ makers → roots + binary trees + cross-root exchanges
8

Primary model authors and self-assesses one position

The original question is wrapped in an untrusted-data envelope. The system requires one object containing statement, way of knowing, locator, restatement, value-laden flag, optional claim type, steelman, critic, evidence, context, ambiguity, and fallacy assessments.

Question text is explicitly declared untrusted data, reducing prompt-injection risk.
One call both authors the position and supplies the scores used to judge it.
9

Every provider attempt is bounded and recorded

The gateway enforces max attempts, token ceiling, deadline, contract hash, and input hash. Raw HTTP artifacts and ledger outcomes persist. Parse/schema failures append a machine-error repair prompt and retry. Transport failures become typed FAILED/TIMED_OUT; optional cooldown/final retry can apply.

10

Code classifies the original question

Keyword regexes resolve empirical, causal, normative, definitional, prediction, comparative, mixed, or unknown. Unknown may use the model’s closed-vocabulary suggestion. Scope extraction attempts timeframe, geography, population, and URL locators.

Every child uses the original question as claimClassificationLine; one claim frame controls all node reducers even if a child has a different local claim type.
11

Assessment reduces deterministically to base strength τ

metrics = {
  steelman_fidelity,
  counter_resilience = 1 − counterargumentStrength,
  evidence_quality, evidence_relevance, context_fit,
  clarity = max(0, 1 − ambiguityDecay × ambiguityCount),
  fallacy_resilience = 1 − fallacySeverity
}
τ = clamp(Σ(metric × register coefficient), 0, 1)
τ = min(τ, each matching fatal-flag cap)

The original-question claim-type register cell supplies coefficients, ambiguity decay, caps, and uncertainty ladder. Missing row/cell is a loud failure. Fatal flags also become uncertainty drivers and assessment holes.

Selection receives one candidate. Earned weight affects recorded selection score, but selected τ remains the authoring model’s τ.
12

Root node and provenance are persisted

The graph node stores statement, claim type, path metadata, way of knowing, locator, value-laden flag, and artifact reference. Separate rows store stranger restatement and reduced judgement details.

LOOKED_UP survives only with a locator. Every other returned value—including RAN—becomes REASONING.
PHASE 03

Debate graph: positions, branches, and review coverage

13

Other makers author independent roots

Each additional healthy configured maker authors an independent position without grading or imitating another maker. Each root repeats steps 8–12 and gets its own statement, self-assessment, τ, restatement, and provenance.

14

Every root receives a breadth-first binary pro/con tree

root
├── strongest genuine support
│   ├── support for that support
│   └── attack on that support
└── strongest genuine counter-position
    ├── support for that counter-position
    └── attack on that counter-position

Each round doubles the frontier. Author rotates by (rootIndex + round) mod makerCount. Support uses sibling ordinal 1; attack uses 2. Failed authoring halts the planned subtree and records UNAUTHORED-BRANCH-HALTED.

tree nodes = M × (2^(depth + 1) − 1)
cross-root nodes = M × (M − 1)
total = M × (2^(depth + 1) − 1) + M × (M − 1)
M=2, depth=2 → 14 tree nodes + 2 exchanges = 16
15

Ordered cross-root responses connect makers

For every ordered distinct pair, a maker writes one response that supports its own root and attacks the other root. Two makers create two response nodes.

16

Arguments create structural—but unmeasured—edges

{ sourceNodeId, targetNodeId,
  polarity: "support" | "attack",
  strength: null,
  magnitudeStatus: "UNKNOWN",
  strengthSource: "EVIDENCE_VERIFIER" }

A strong child is not automatically a strong influence: node strength and edge strength are independent.

No later live organ measures these generated edge magnitudes.
17

Different-maker reviews land at round boundaries

Roots are reviewed, then new nodes between rounds, then exchanges. Reviewer rotation avoids the author. Output is agree, dispute, or cannot-assess plus reasons.

Outcome does not change τ, edge magnitude, polarity, or verdict. Any review row—including dispute/cannot-assess—counts as reviewed.
18

Judged standing is a fixed-point coverage projection

Directly reviewed nodes seed basis sets. Basis travels upward through child-parent and incoming-edge relationships until no set changes. Unreviewed nodes with reviewed descendants can receive derived standing; nodes with no basis leave the scoring snapshot.

direct review row → reviewed
reviewed descendant/source → derived-standing ancestor
no reviewed basis → HIDDEN-UNJUDGEABLE
PHASE 04

Propagation: graph snapshot → served number candidate

19

Propagation recursively computes strengths

  • Validate references, unit intervals, arrow order, and operator resolution.
  • Derive measured undercut reductions.
  • Lift arrows from folder/unjudged targets to a judged ancestor when possible.
  • Cluster correlated edges by target, polarity, provenance, producing run, and model family; retain the strongest member.
  • Recursively compute sources before targets.
  • Measured contribution = edge strength × source final strength.
  • Aggregate support with accumulate or strict-and; attacks use probabilistic aggregation.
  • Run rival-operator and leave-one-node-out sensitivity passes for audit.
agg(values) = 1 − Π(1 − value)

if attack ≥ support:
  final = τ − τ × (attack − support)
else:
  final = τ + (1 − τ) × (support − attack)
UNKNOWN edges: accumulate skips them, so a root normally stays at τ. Strict-and withholds a target when an unknown support conjunct exists; generated roots can become unservable.
20

Eligible root selection is ordered, not competitive

The propagation receipt stores strengths, lineage, fingerprint, operator, clustering, lifts, rival results, and sensitivity. Roots with a propagated strength are eligible.

servedRoot = first eligible root in configured-provider order
No highest-score, vote, agreement, or debate-winner selection. Low-score threshold only adds HIDDEN-LOW-SCORE; it does not disqualify a root.
PHASE 05

Serve: selected root → cleared prose

21

Fact bundle contains one selected-root fact

{
  facts: [servedRoot.statement],
  residualObjections: [],
  badges: [],
  conditionMarks,
  reversalPoint: servedRoot.selfAssessment.critic.summary,
  buildsOnPrevious,
  memoryDisclosure
}
Other positions/branches are excluded. Residual objections are hardcoded empty, so their gate passes vacuously. Reversal point is the root author’s own critic summary.
22

Primary provider composes at most two segments

It receives the fact bundle, one available node named primary, and reference number:final-strength. It must preserve facts, add none, and cite only supplied references.

It receives the number reference but not the actual numeric strength, so it cannot reason about or accurately state that value.
23

Serve gates can force components-only

  1. Load-bearing root restatement must be PASS.
  2. Residual-objection array must be empty.
  3. UTF-8 byte length of serialized fact bundle must fit selected composition tier.
  4. Cost envelope may skip enrichment; protected-core exhaustion becomes ENVELOPE_EXHAUSTED, distinct from DEFECT.
gate failure → terminal COMPONENTS_ONLY
              answerForm null
              confidenceBand null
              condition mark DEFECT or ENVELOPE_EXHAUSTED
24

Conformance checks every load-bearing segment

A model judges each segment against the frozen bundle. Non-load-bearing segments are exhaustive or deterministically sampled by segment-ID hash. Failure triggers one recomposition; a second failure becomes components-only.

compose 1 → conform
  pass → continue
  fail → compose 2 → conform
            fail → COMPONENTS_ONLY + DEFECT
25

Way of knowing decides answer form and terminal

valid LOOKED_UP + locator
  → SERVED + answerForm VERDICT

all REASONING
  → segment 1 hypothesis
  → segment 2 research plan
  → DOWNGRADED + HYPOTHESIS_WITH_RESEARCH_PLAN

LOOKED_UP without locator
  → COMPONENTS_ONLY + DEFECT
RAN is normalized to REASONING, leaving authored roots effectively LOOKED_UP-with-locator or REASONING.
26

Post-compose R9 checks final wording

A conformance-role model sees the original question and final segments and returns only { pass }. Failure suppresses prose into components-only.

27

Confidence band is capped by basis—not score

The runner counts load-bearing LOOKED_UP/RAN/REASONING nodes. Register cuts cap the candidate band and provide label, source, and lift path. A cap still serves. Mono-maker runs lower the candidate one step before the ceiling.

Confidence band and verdict state are independent.
PHASE 06

Finalize: recorded facts → answer row → UI

28

Terminal battery activations are drained

WAIT rows are evaluated from recorded facts. ACTIVE without execution adds OWED-CHECK-UNEXECUTED. Question-type fallback adds UNRESOLVED-TYPE-FALLBACK. These marks do not map the verdict to CONTESTED/UNSUPPORTED.

29

Selected root strength becomes the served number

{ numberRef: "number:final-strength",
  value: selectedRoot.finalStrength,
  numberKind: "propagated-probability",
  sourceRef, producer, replayHandle, propagationRunId }

The number persists separately from prose. Pre-composition components-only omits it; some post-composition components-only may retain it but still cannot produce a verdict state.

30

Verdict state uses one Boolean—not the score

usableBasis = servedNumber exists
              AND terminal ∈ { SERVED, DOWNGRADED }

usableBasis ? verdict_state = SUPPORTED
            : verdict_state = null + unavailable reason
No thresholds map strength to SUPPORTED/CONTESTED/UNSUPPORTED. Score 0.05 can be SUPPORTED if gates pass; 0.95 can be unavailable if a gate fails. CONTESTED and UNSUPPORTED are schema-declared but unreachable here.
31

Answer, evidence, and terminal persist atomically

The repository inserts fact bundle, composed text, conformance, answer form, terminal, serve state, verdict state, band, condition marks, served-number event, and run TERMINAL event. The work settles with answer ID; racing workers return the winning artifact.

32

UI refreshes on terminal event

The debate page streams events, updates live node state, and reloads on run.terminal. The banner separately displays verdict state, confidence band, unavailable reason, and serve state; the graph stays inspectable.

Reading guide

Decision seams, not automatic fixes

Start with the red critical path: production wiring → independent judgement → edge measurement → root selection → verdict mapping.

Critical · executable

Production runner stops before work

Main omits judgement policy, serve policy, terminal evaluator, and multi-maker/scoring wiring.

Questions: Which sealed rows populate them? Should startup fail before worker registration? How does production mirror acceptance gateway/probe wiring?
Critical · epistemic

Author also supplies its score

Same call authors and grades; selection has one candidate.

Questions: Separate author from judges? How many judges? How should family correlation, dispersion, abstention, and disagreement affect confidence without averaging away dissent?
Critical · causal

Debate edges stay UNKNOWN

Accumulate leaves root at τ; strict-and may withhold it.

Questions: What independent verifier measures relevance/influence? Are support/attack symmetric? How are undercuts and correlated evidence calibrated?
Critical · decision

First eligible provider always serves

Order—not score or outcome—selects the root.

Questions: Is the product serving one perspective, adjudicating, or synthesizing? Choose a rule: max strength, Pareto set, pairwise comparison, vote, risk-aware abstention, or multi-answer display.
Critical · verdict

Verdict collapses to SUPPORTED/null

Strength never enters verdict derivation.

Questions: What does strength mean? Which claim/risk cuts create states? Should disagreement, residual objections, uncertainty, or sensitivity create CONTESTED or abstention?
High · critique

Review existence matters; outcome does not

Agree, dispute, cannot-assess all seed standing equally.

Questions: Should cannot-assess count? Should dispute create attack, lower band, reopen scoring, or live as a separate disagreement dimension?
High · composition

Composer sees one root, no objections, no value

Other nodes excluded; objections empty; only number reference is passed.

Questions: Include strongest objections, other positions, score, sensitivity, uncertainty? Which facts are load-bearing? How can prose summarize disagreement without new facts?
High · control

Steering is recorded but inert

Stored in askContract, omitted from runner head.

Questions: Should steering affect prompts, branch priority, values, or disclosure only? How is untrusted free text isolated and replayed?
High · evidence

RAN collapses to REASONING

Only LOOKED_UP with locator survives.

Questions: What execution receipt proves RAN? How are tool outputs attested? Should locators be independently resolved?
Medium · typing

Original question type controls every child

A normative debate’s empirical child still uses normative composition.

Questions: One decision frame plus local node type? Which reducer controls credibility versus influence? How are mixed claims decomposed?
Medium · gates

Residual-objection gate is vacuous

Runner always creates an empty array.

Questions: Who selects unresolved attacks? Should they block, contest, lower score, or appear as caveats?
Medium · reliability

Restatement and conformance are model judgements

Author declares restatement; primary composes; conformance-role model checks.

Questions: Independent provider? Which checks deterministic? How do we calibrate false passes and correlated error?
Medium · cost

Depth multiplies calls exponentially

Binary expansion plus every ordered root exchange; normally author + review per node.

Questions: Adapt depth to leverage, uncertainty, novelty, or budget? Collapse duplicates? Which branches deserve depth?
Medium · semantics

“Verdict” names three things

Terminal, answer form, and verdict state are adjacent but distinct.

Questions: Separate evidence clearance, prose form, support category, and confidence. What does SUPPORTED mean when the answer is a reasoning hypothesis?

Actual decision logic

ask = validate(form)
admission = resolveRiskPanelBudget(ask)
run = freezeEncryptQueue(ask, admission)

requirePoliciesOrFail()
makers = recheckPinnedPanel(run)

for each node in roots/tree/exchanges:
  artifact = modelAuthorsAndSelfAssesses()
  type = classifyOriginalQuestion()
  tau = reduce(artifact.assessment, register[type])
  persistNode(node, tau)
  persistEdges(strength=null, UNKNOWN)

for each node:
  persistDifferentMakerReview(any outcome)

snapshot = keepAnyReviewedBasis()
strengths = propagate(snapshot)
servedRoot = eligibleRoots[0]

facts = {
  selectedRootStatement,
  residualObjections: [],
  rootSelfCriticSummary,
  honestyMarks,
  memory
}

result = composeAndGate(facts)
number = resultNeedsEvidence ? root.strength : null
usable = number != null
         && terminal in [SERVED, DOWNGRADED]
verdict = usable ? SUPPORTED : UNAVAILABLE
persistEverything()
