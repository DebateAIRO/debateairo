# Finite social identity relay

Source preparation only; this template has not been installed and does not establish any provider's credentials, entitlement or paid access. Keep the API's existing Internet denial. Only its Unix socket client joins `debateai-social-clients`; the worker owns no DB, user DEK, KEK, staff/Owner, mail or model-provider credentials.

The API's optional `SOCIAL_PROVIDERS_JSON` is an array of closed public records `{provider,clientId,appScope,access:"existing-approved"}`. It derives each callback from the already validated PUBLIC_APP_URL and hashes provider/client/scope/callback into the immutable configuration binding. `SOCIAL_SOCKET_PATH` names `/run/debateai-social/identity.sock`. Invalid social configuration emits a constant diagnostic and advertises no provider. Missing socket, capability mismatch, credentials or previously approved access also advertises none. No model provider discovery variable is reused.

The separate systemd `social-providers` credential is a closed object keyed by provider. Every entry contains the same clientId/appScope, exact HTTPS callback, and access value. Google/X/Facebook entries additionally have clientSecret. Apple instead has teamId, keyId and its EC P-256 privateKey; its appScope must equal teamId + "." + clientId so a team change invalidates the public capability binding. The loader requires the private directory and file to belong to the service UID, no group/other permission bits, no symlink, and at most 32 KiB. It clears inherited environment before loading; proxy/debug/DNS/TLS override variables are rejected. The API does not read this credential.

The worker exposes POST `/social` only on the Unix socket. Finite operations are capabilities, google.exchange/keys, apple.exchange/keys, facebook.exchange and x.exchange. Callers cannot supply URL, redirect URI, headers, access token, issuer or JWKS location. Code exchange, token inspection and User lookup use fixed HTTPS hosts/paths/methods with normal certificate verification and redirects refused. Only bounded ID tokens/JWKS or inspected minimal user fields leave the worker; access/refresh tokens and secrets do not. Requests are at most 8192 bytes, responses 65536 bytes, deadline 5000 ms including upload/parse/provider work, concurrency 32 with no wait queue. The API's JWKS cache has at most 16 keys per provider, five-minute TTL, one refresh in flight and one refresh attempt per 30 seconds, including failed/unknown-key attempts.

Google requests openid/email/profile with S256 PKCE. Apple requests name/email with confidential code exchange, transaction nonce and form_post; no unsupported Apple PKCE is sent. Facebook's candidate adapter pins the independently checked v26.0 exchange/debug/me contract and always requires local email proof. Its capability is source-disabled pending reviewed current manual-web code-injection/PKCE semantics plus actual app access/cost certification. X requests only tweet.read/users.read/users.email, uses S256 PKCE, and fetches only id/name/confirmed_email. No People, phone, contact, avatar or offline operations exist.

Apple Developer access and X User Read costs remain external activation dependencies. An `existing-approved` value is an operator assertion about access already established and approved; fixtures or a successful mock do not constitute that evidence. Do not enroll, purchase, activate credits or change a provider dashboard from this source change. Current official callback registration, real provider tests, actual Unix permission separation, TLS/redirect/oversize/deadline tests against the installed worker and positive/negative API/worker egress confinement proofs belong to release acceptance. Host firewall policy must enforce the reviewed worker egress posture before enablement; this unit alone is not a measured network isolation claim.
